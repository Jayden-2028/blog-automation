## 1. 시작 전 필수 로딩

**아래를 모두 읽기 전에는 한 글자도 쓰지 않는다.** 하나라도 못 읽으면 중단하고 사람에게 알린다.
목록의 유일한 출처는 `src/workflows/writing/specFiles.ts`이며, 클라우드·맥 로컬·대화형 세션 모두 같다.

| # | 대상 | 목적 |
|---|---|---|
| 0 | `research/[키워드].md` | 원고의 **사실 전부**. 여기 없는 사실은 못 쓴다 |
| 1 | **`prompts/writing/core-rules.md`** | 한 페이지 핵심 규칙. **다른 문서와 부딪히면 이 파일이 이긴다** |
| 2 | `rules/facts-and-hedging.md` | 사실 태도 상세 사례 |
| 3 | `style/voice.md` (incident는 `style/incident.md`) | 공통 어투·어미·인칭 |
| 4 | `style/{parenting,entertainment,trend,incident}.md` | 카테고리별 제목 기법·흐름 |
| 5 | `rules/article-structure.md` | 유형별 소제목 **순서** |
| 6 | `rules/topic-allocation.md` | 내적/외적 **비중** |
| 7 | `rules/output-format.md` | 서식·저장 형식·윤문 (코드가 파싱) |
| 7-1 | `rules/images.md` | 이미지 마커·획득 방식 판정·프롬프트 쓰는 법 |
| 8 | `docs/seo-guide.md` | 제목·키워드·태그 수치 (충돌 시 위 문서가 이긴다) |

### 우선순위 (충돌 시)

```
core-rules.md  >  사실·헤지 상세  >  voice.md 어투  >  구조(article-structure·카테고리 파일)  >  seo-guide  >  관행
```

SEO 규칙을 지키려고 어투나 사실 태도를 바꾸지 않는다. 구조·수치 규칙(분량·태그 수)은 문체를 해치지 않으므로
그대로 따른다. `rules/output-format.md` §6에 실제 충돌 사례와 해소법이 있다.

## 2. 카테고리 라우팅 — 계정 스킬이 아니라 저장소 파일이다

리서치 파일의 `topic`과 내용을 보고 **하나만** 고른다. 섞지 않는다. 계정 레벨 스킬
(`/parenting-blog-writer` 등)은 쓰지 않는다 — 클라우드 헤드리스에서 로드되지 않고 맥과 규격이 갈라지기
때문이다. 구조·제목 규격은 항상 아래 저장소 파일이다.

| 조건 | 읽을 파일 |
|---|---|
| **사망·범죄·재난·수사/재판** (다른 분야 단어가 섞여 있어도 항상 이긴다) | `style/incident.md` |
| 육아·임신·출산·영유아 건강/발달/교육, 가족 생활 | `style/parenting.md` |
| 넷플릭스·드라마·영화·예능·연예 뉴스·OTT | `style/entertainment.md` |
| 정책·지원금·제도, 사회 이슈, 밈·바이럴, 논쟁 사안, 미분류 | `style/trend.md` |

애매하면 **글의 목적**으로 가른다(제도 안내 = trend, 우리 집 이야기 = parenting). 그래도 애매하면 사람에게 묻는다.

- 공통 자산: 후킹 제목 기법(반전형·손해회피형·감탄 수식어·인용 직접화법·숫자 전면 배치).
- "저도 궁금해서 찾아봤어요" 같은 탐구 프레이밍은 공통 자산이 아니다. 오프닝은 소재를 바로 던진다.
  parenting만 화자가 실제 쌍둥이 부모라 경험담 오프닝이 진짜 목소리다.

### 2-1. 사건·사고(`incident`)

`style/incident.md`가 **유일한 규격**이다(무죄추정·신원 보호·자극적 세부 금지·감정 자극 제목 금지·
1인칭 금지·전 문장 합니다체·담담한 마무리). 이 문서의 다른 절과 부딪히면 incident.md가 이긴다.
연예인이 얽혀도 내용이 범죄·사망이면 incident다. 사건이 아니라 작품·활동이 주제면 해당 카테고리다.
판단이 서지 않으면 사람에게 묻는다 — 잘못 쓰는 비용이 크다.

## 3. 입력 계약

```yaml
keyword: 아기 밤중수유 끊는 시기      # 필수. research 파일명과 동일
research_file: research/아기-밤중수유-끊는-시기.md   # 필수
episode: |                          # 선택. 실제 경험 메모(parenting)
  지난주 지우가 새벽 3시에 깨서 40분을 울었음. 지아는 그날 안 깼음.
```

### 3-1. 기획 브리프는 뼈대가 아니라 재료다

```
구조(소제목 순서)   article-structure.md 의 유형별 단계   ← 1순위
비중(분량 배분)     topic-allocation.md 의 내적/외적
내용(단계 속 재료)  브리프 Q + 리서치
```

브리프(독자 질문 Q1~Q5·후킹 포인트·독자 행동)는 **자료조사 전에 제목만 보고** 만든 추정이다.

- 소제목은 유형별 단계 순서를 따른다. 질문 문장을 그대로 소제목으로 쓰지 않는다 — 답의 핵심 키워드를 뽑은
  6~20자 단문이다(`seo-guide.md` 규칙 2). 질문 형태는 `자주 묻는 질문` 블록에서만 쓴다.
- **리서치가 브리프와 어긋나면 리서치를 따르고**, 틀린 전제는 질문째 버리거나 바꾼다. frontmatter에
  `brief_revised: Q2(케미 -> 직장인 공감)`으로 남긴다.
- **리서치에 답이 없는 질문은 채우지 않는다.** 그 소제목을 빼고 frontmatter에 남긴다:
  `brief_coverage: 4/5` / `unanswered: Q5`. (본문에 "확인되지 않았습니다"를 쓰지 않는다 — core-rules §1)
- 브리프가 없으면 리서치와 카테고리 파일로 구조를 잡는다.

### `episode`가 없을 때 — 경험을 지어내지 않는다

있지도 않은 병원 방문, 지아·지우의 가짜 일화, 겪지 않은 시청 경험은 쓰지 않는다. 순서:
1. 리서치 `## 5. 사람들이 실제로 묻는 질문`을 오프닝 소재로 쓴다.
2. 특정 사건을 특정하지 않는 일반화된 관찰로 대체한다("쌍둥이를 키우다 보면 ~한 순간이 옵니다").
3. 그래도 오프닝이 서지 않으면 **초안을 멈추고 사람에게 에피소드를 요청한다.**

## 5. 제목

seo-guide의 수치 규칙과 후킹 기법을 **동시에** 만족시킨다.

- 공백 포함 **25~40자**, 메인 키워드를 **앞쪽 1/3 안에** 원형 그대로(띄어쓰기 변형 금지)
- 후킹 프레이밍은 키워드 **뒤에** 붙인다. 같은 키워드 2회 반복·특수문자 남발 금지
- 제목이 던진 질문에 첫 문단이 답한다. 카테고리별 후킹은 카테고리 파일을 따른다(엔터는 작품명 노출 + 최상급/느낌표, 트렌드는 손해회피형·반전형, incident는 후킹 금지)

```
(X) 저희 쌍둥이 밤중수유 끊었던 이야기          → 키워드가 흐릿함
(X) 밤중수유 끊는 시기 밤중수유 끊는 법 총정리   → 반복
(O) 아기 밤중수유 끊는 시기, 6개월설이 전부는 아니었어요
```

## 11. 이미지 자기 점검 (상세 규칙은 `rules/images.md` §8)

- [ ] `[IMAGE:]` + `[IMAGE PROMPT:]` 쌍이 짝이 맞는다(엔터·연예·OTT는 개수 상한 없음, 그 외 5개 이상)
- [ ] 각 마커가 **바로 위 문단이 무엇에 관한 것인지**(누구·무엇) 보여준다. 문단 내용을 다 담으려 하지 않는다 - 건물 외관·일반 장면으로 대역하지 않는다(2026-10-02). 실존 인물·특정 방송처럼 대상이 정해진 `웹 검색` 자리는 둘째 줄을 **이름 2~4단어**로 쓴다
- [ ] 자리마다 §8-4의 질문(웹 검색 → 페이지 캡처 → 글자 정보면 자리 없음 → AI 생성)을 순서대로 적용했다. AI 생성은 폴백이다
- [ ] `표 생성` 마커 0개, **언론사 기사 화면 캡처 0개**(2026-10-02 폐지), 법령·정부 포털 화면 캡처 0개, 특정 날짜의 회의·발표 현장 0개, 실존 인물·브랜드·로고 생성 0개
- [ ] `페이지 캡처` URL은 리서치 `## 11. 캡처할 페이지`에 있는 것만. `AI 생성` 프롬프트는 영어 + `no text, no letters` + 비율. 어떤 프롬프트에도 지시문이 없다

## 12. 실패 처리

| 상황 | 조치 |
|---|---|
| 리서치 파일 없음 / `verdict: blocked` | 작성 중단. 사람에게 알림 |
| 규격 파일 로딩 실패 | 작성 중단. 규격 없이 쓰지 않는다 |
| 카테고리 판단 불가 | 사람에게 질문 |
| `episode` 없고 대체 오프닝도 안 섬 | 초안 보류, 에피소드 요청 |
| 필요한 수치가 리서치에 없음 | 그 문장을 쓰지 않고 `<!-- 확인 필요 -->` 주석에 남긴다 |
| 윤문 결과 30% 이상 변경 경고 | 윤문 결과 폐기, 원인 확인 후 재시도 |
| 2,000자를 못 채움 | 리서치가 얇은 것. **문장을 늘리거나 같은 정보를 반복해 채우지 않는다.** `thin`이면 미달 그대로 저장한다(검수 카드가 "자료 얇음"으로 알린다) |
| 3,000자를 넘김 | 주제가 둘 이상 섞인 것이면 쪼갠다. **정보성 원고(event·product·policy·living)는 쪼개지 않는다** |
| 미확정·비공개 정보라 단정할 수 없음 | 그 항목을 쓰지 않는다(core-rules §1-4) |
| 실존 인물·작품 이미지가 필요함 | AI 생성 대신 `웹 검색`, 검색어는 **이름만 2~4단어**(images.md §8-1-1) |
| TV 화제성·박스오피스 순위가 필요함 | 우리가 못 그린다. `페이지 캡처` + 리서치 §11 URL(§8-4) |
| 법령·정부 포털 화면을 보여주고 싶음 | 캡처하지 않는다(§8-2). 현장 실사로 바꾸고 조문·수치는 본문에 쓴다 |
| 리서치 §11에 마땅한 URL이 없음 | `페이지 캡처`를 쓰지 않고 웹 검색 → AI 순으로 다시 판정한다 |
| 특정 회의·발표 현장 사진이 꼭 필요해 보임 | 만들지 않는다(§8-3). 제도가 적용되는 일반적 현장으로 바꾼다 |
