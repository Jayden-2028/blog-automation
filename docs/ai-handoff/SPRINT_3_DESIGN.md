# Sprint 3 설계 — 검수 게이트 + 이미지

작성일: 2026-08-28 · 상태: **승인 완료** (결정 항목 5건, §15 참고) · 구현 진행 중

## 1. 배경

Sprint 2로 "키워드 선택 → 조사 → 사람 확인 → 원고 생성 → Telegraph로 읽기"까지 닫혔다.
실측 3건(경복궁 별빛야행 / 아기 셔더링어택 / 재혼 황후 / 아이폰18) 후 남은 구멍은 두 가지다.

**구멍 1 — 원고 품질을 아무도 검증하지 않는다.** 사용자 질문("원고 퀄리티에 대한 품질 관리는
이후 스프린트에서 할 수 있는지")이 정확히 이 지점이다. 지금은 원고가 만들어지면 그대로 사람에게
가고, 본문이 팩트 카드를 벗어났는지·추측성 표현이 섞였는지·분량이 목표를 넘었는지 아무도 보지
않는다. 실제로 아이폰18 원고는 3,304자로 목표(1,500~2,500)를 32% 초과했는데 아무 신호도 없었다.

**구멍 2 — 비의학 원고에는 승인 버튼이 없다.** 현재 확인/수정/폐기 버튼은 의학 주제 교차확인
전용이다(`requiresMedicalReview` 플래그를 내리는 용도). 엔터/생활 원고는 "원고 보기" 링크만
가고 승인 여부를 기록할 방법이 없다 - job이 `review` 상태에 영원히 머문다.

그리고 로드맵상 Sprint 3의 나머지 절반인 **이미지**는 아직 생성 경로 자체가 정해지지 않았다.

## 2. 목표와 비목표

**목표**

- 원고 생성 직후 자동 검수를 돌려 그 결과를 사람에게 함께 보여준다
- 모든 원고에 공통 승인 흐름(승인/수정/반려)을 붙이고 `job.status`를 `approved`로 전이시킨다
- 이미지 조달 경로를 하나 확정하고, 저작권 근거를 함께 기록하는 배선을 만든다

**비목표(이번 스프린트에서 하지 않는 것)**

- 네이버 실제 발행 — Sprint 4
- 이미지를 본문 안 특정 위치에 자동 배치 — 발행 경로(SmartEditor)가 정해진 뒤에 의미가 있다
- 검수 실패 시 자동 재작성 — 재작성 루프는 비용이 곱으로 늘고, 무엇을 고쳐야 하는지에 대한
  데이터가 아직 없다

# 파트 A — 검수 게이트

## 3. 검수를 언제 돌리는가

`runWritingStage` 안, `createArticleForJob` 직후 · Telegram 알림 직전에 자동으로 돌린다.
별도 CLI 단계(`job:review`)로 분리하지 않는다.

조사 체크포인트는 사람이 개입할 값싼 지점을 만들려고 분리했지만(비싼 LLM 호출을 막는 게 목적),
검수는 규칙 기반이라 비용이 사실상 0이고 결과가 곧 알림 내용의 일부다. 분리하면 사람이 명령을
한 번 더 쳐야 하는데 그 대가로 얻는 게 없다.

## 4. 무엇을 검사하는가

규칙 기반으로 한다(LLM 호출 없음). 이유는 §5.

각 항목은 `error`(사람이 반드시 봐야 함) / `warning`(참고) 중 하나의 심각도를 갖는다.

### 4-1. 팩트 — 본문의 숫자·날짜가 근거에 있는가

가장 가치가 높은 검사다. 환각을 직접 잡는다.

본문에서 숫자·날짜·금액을 뽑아 `sources[].content` 전체와 대조한다. 근거에 없는 값이 나오면
`error`로 표시한다.

정규화가 핵심이다. 모델은 근거의 표기를 그대로 쓰지 않는다:

```
근거: "2026. 9. 2.(수) ~ 10. 24.(토)"
본문: "9월 2일부터 10월 24일까지"      ← 같은 사실, 다른 표기
근거: "60,000원"
본문: "6만 원"                          ← 같은 값, 다른 표기
```

그래서 대조 전에 양쪽을 정규화한다: 날짜는 `YYYY-MM-DD`/`MM-DD`로, 금액은 한글 단위(만/천)를
풀어 숫자로, 구분자(`,` `.` 공백)는 제거한다. 정규화로도 못 맞추는 표기가 남을 수밖에 없으므로
**이 검사는 "틀렸다"가 아니라 "근거에서 확인되지 않았다"로 표기한다** - 사람이 최종 판단한다.

일반 상식 수치(연도, 1인, 2개 등)의 오탐을 줄이기 위해 한 자리 숫자와 흔한 서수는 제외한다.

고유명사 대조는 v1에서 하지 않는다. 한국어 고유명사 추출은 형태소 분석 없이는 오탐이 너무 많고,
그 비용(품질·구현 모두)이 얻는 것보다 크다.

### 4-2. 법적 — 추측성·단정성 표현

형법 307조 리스크(로드맵 §6-2). 어휘 규칙으로 충분히 잡힌다.

```
탐지 대상: "~라는 의혹", "~로 보인다", "~한 듯", "~라는 설", "루머", "카더라",
          "~일 가능성이 크다", "~로 추정된다"
```

인물명이 함께 등장하는 문장에서 발견되면 `error`, 그 외에는 `warning`으로 낮춘다. 아이폰
출시일 전망 같은 제품 기사에서는 "~로 예상된다"가 정당한 표현이지만, 인물 관련에서는 아니다.

### 4-3. 광고 — 대가성 표시 누락

본문에 대가성 어휘(협찬, 제공받아, 원고료, 무상 제공)가 있는데 표시 문구(`#협찬`, `#광고`,
"소정의 대가")가 없으면 `error`.

지금은 협찬 원고를 만들지 않으므로 발화할 일이 거의 없다. 그래도 넣는 이유는 나중에 협찬이
생겼을 때 이 검사가 없으면 **표시광고법 위반이 조용히 나간다**는 점이다. 비용이 거의 없는
보험이다.

### 4-4. 품질

| 검사 | 기준 | 심각도 |
|---|---|---|
| 분량 | `TARGET_ARTICLE_LENGTH`(1,500~2,500자) 벗어남 | warning |
| 제목-본문 일치 | 제목의 핵심 어절이 본문에 없음 | warning |
| 중복 문장 | 같은 문장이 2회 이상 | warning |
| 참고 자료 | "참고 자료" 섹션과 링크가 없음 | error |
| 해시태그 | 15개가 아님 | warning |
| 의학 고지 | 의학 주제인데 고지 문구가 없음 | error |

마지막 두 개는 Sprint 2에서 코드로 붙이도록 한 것들이다(`buildMedicalDisclaimer`, `HASHTAG_COUNT`).
코드가 붙이므로 실패할 일이 없어 보이지만, 검사를 두는 이유는 **붙이는 코드가 나중에 깨져도
조용히 지나가지 않게** 하기 위해서다.

## 5. 왜 규칙 기반인가 (LLM 검수를 쓰지 않는 이유)

원고 1건에 이미 LLM을 두 번 쓴다(조사 요약 ~30초, 원고 생성 ~180초). 검수까지 LLM으로 하면
세 번째다. 그런데 위 항목은 전부 결정적 규칙으로 핵심을 잡을 수 있고, 규칙 기반은:

- 비용 0, 지연 0
- 결정적이라 테스트로 고정할 수 있다(회귀가 잡힌다)
- "왜 걸렸는지"를 정확히 지목할 수 있다(LLM은 근거를 지어낼 수 있다)

**한계는 분명히 기록한다**: 규칙은 "본문이 근거를 의미적으로 왜곡했는가"를 못 잡는다. 숫자는
맞는데 인과관계를 뒤집어 쓴 경우 등이다. 이건 사람 검수가 담당하고, 데이터가 쌓여 어떤 왜곡이
실제로 자주 나오는지 알게 되면 그때 LLM 검수를 검토한다.

## 6. 결과를 어떻게 다루는가 — 차단하지 않는다

**검수 실패가 원고를 사람에게 못 가게 막지 않는다.** 결과는 알림에 함께 표시되고, 사람이 보고
판단한다.

이유가 셋이다. (1) 어차피 발행 전 사람 승인이 필수라 이중 게이트가 된다. (2) 오탐률에 대한
데이터가 0인 상태에서 차단하면 멀쩡한 원고가 조용히 사라진다. (3) 규칙이 잡는 건 "확인이
필요한 지점"이지 "확정된 오류"가 아니다(§4-1 참고).

알림 형태:

```
📝 원고 초안 준비됨
아이폰18·첫 폴더블 아이폰, 출시일과 가격 전망 정리
키워드: ... · category: living
근거: 공공 0 · 의료 0 · 뉴스 5 · 커뮤니티 10
작성 소요 시간: 176초

⚠️ 검수 3건 (오류 1 · 경고 2)
· [팩트] "300만원"이 근거에서 확인되지 않음
· [품질] 분량 3,304자 (목표 1,500~2,500)
· [법적] 추측성 표현: "~로 예상된다"

[📄 원고 보기]
[✅ 승인] [✏️ 수정 필요] [🗑 반려]
```

검수가 전부 통과하면 `✅ 검수 통과` 한 줄만 넣는다.

## 7. 저장 위치 — `review_checks` 테이블 대신 job metadata

로드맵은 `review_checks` 테이블 신설을 적어뒀지만, **v1은 `article_jobs.metadata.reviewChecks`에
JSON으로 저장할 것을 제안한다.**

- 이 저장소의 migration은 CLI 없이 Dashboard SQL Editor로 수동 적용해야 한다(사용자 승인 필요).
  얻는 것에 비해 비용이 크다.
- 하루 1~2건 규모에서 "어떤 검사가 자주 걸리는가"는 PostgREST의 JSON 연산자로 충분히 뽑을 수 있다.
- 나중에 검수 이력이 실제로 커지면 그때 테이블로 옮긴다. metadata에 이미 쌓인 데이터를
  migration으로 옮길 수 있으므로 되돌릴 수 없는 선택이 아니다.

## 8. 공통 승인 흐름 — 의학 전용 버튼을 흡수한다

지금 `review:<action>:<jobId>` 콜백(confirm/edit/discard)은 의학 교차확인 전용이고, confirm이
`job.status`를 바꾸지 않는다("발행 승인은 이후 검수 단계에서" — 그 단계가 바로 지금이다).

**제안: 같은 콜백을 모든 원고의 승인 흐름으로 승격한다.**

| 액션 | 라벨 | 하는 일 |
|---|---|---|
| `confirm` | ✅ 승인 | `job.status` → `approved`, `articles.status` → `approved` |
| `edit` | ✏️ 수정 필요 | `review` 유지 + `reviewDecision: "needs_edit"` 기록 |
| `discard` | 🗑 반려 | `job.status` → `rejected` (기존과 동일) |

의학 주제는 여기에 **한 겹을 더한다**: `requiresMedicalReview`가 켜져 있으면 승인 시 그것도 함께
내리고 `medicalReviewedAt`을 남긴다. 즉 의학 원고의 승인은 "발행 승인 + 교차확인 완료"를 동시에
뜻한다. 버튼을 두 벌 만들지 않는 이유는 화면에 버튼 6개가 뜨면 무엇을 눌러야 하는지 알 수 없기
때문이다.

**⚠️ 이 변경은 기존 의미를 바꾼다**: 지금까지 confirm은 status를 건드리지 않았다. 이미 confirm이
눌린 job("아기 셔더링어택")은 `review` 상태로 남아 있는데, 새 흐름에서는 다시 눌러야 `approved`가
된다. 되돌릴 수 없는 데이터 변경은 아니므로(수동으로 status만 바꾸면 됨) 그대로 진행할 것을
제안한다.

# 파트 B — 이미지

## 9. 이미지 조달 경로 — ChatGPT (사용자 결정, 2026-08-28)

**결정: ChatGPT를 이미지 서치·제작 에이전트로 쓰고, 실제 검수는 업로드 직전 사용자가 직접 한다.**

### 9-1. 연결 형태 — 수동 핸드오프다

먼저 사실 관계를 분명히 해둔다. 이 저장소에서 쓸 수 있는 ChatGPT 계열 도구는 Codex CLI
(`delegate-codex`)뿐인데 **Codex는 코딩 에이전트라 이미지를 만들지 못한다.** 샌드박스 안에서
코드를 읽고 쓰는 도구이지 DALL·E를 부르는 경로가 아니다.

따라서 실제 흐름은 자동 호출이 아니라 **사람을 거치는 핸드오프**가 된다:

```
[Claude] 원고 확정 -> 이미지 브리프 생성(장면 설명 + 생성 프롬프트 + alt_text 초안)
            ↓ Telegram으로 전달
[사용자]  ChatGPT에서 브리프로 이미지 생성/탐색 -> 결과를 손에 쥔다
            ↓
[사용자]  업로드 직전 직접 검수 (Sprint 4 네이버 임시저장 단계)
```

이건 자동화의 후퇴가 아니라 사용자가 명시적으로 고른 지점이다 — 이미지는 저작권·품질 위험이
가장 크고(로드맵 §6-1), 사람 눈이 마지막에 한 번 들어가는 편이 안전하다.

### 9-2. Claude가 만드는 것 — 이미지 브리프

Claude는 이미지를 만들지 않고 **브리프를 만든다**. 원고를 이미 갖고 있으므로 무엇이 필요한지
가장 잘 아는 위치다.

```
제목: 아이폰18·첫 폴더블 아이폰, 출시일과 가격 전망 정리
용도: 대표 이미지(썸네일)

장면: 접힌 스마트폰의 실루엣을 미니멀하게, 파란 계열 그라데이션 배경
생성 프롬프트(ChatGPT에 그대로 붙여넣기용):
  "A minimal illustration of a folding smartphone silhouette, blue gradient
   background, clean product-render style, no text, no logos, 16:9"
alt_text: 폴더블 스마트폰을 형상화한 일러스트
금지: 실제 애플 제품 사진, 애플 로고, 실존 인물
```

`금지` 항목이 핵심이다 — 브리프 단계에서 저작권 위험을 미리 잘라낸다(§10).

## 10. 서치와 생성은 위험이 다르다 (결정 완료, 2026-08-28)

**결정: 생성을 기본으로 하고, 서치는 공식 보도자료·라이선스 명시 스톡으로만 한정한다.**

사용자 결정에 "이미지 서치, 제작"이 함께 들어 있었는데, **이 둘은 저작권 위험이 완전히 다르다.**
로드맵 §6-1이 "가장 큰 실질 위험"으로 지목한 지점이라 그냥 넘기지 않고 적어둔다.

| | 저작권 | 로드맵 §6-1 분류 |
|---|---|---|
| **생성** (ChatGPT가 이미지를 그림) | 안전 — 우리가 만든 것 | ✅ "직접 생성한 AI 이미지" |
| **서치** (웹에서 기존 이미지를 찾음) | **위험** — 남의 저작물 | ❌ "구글 이미지 검색 결과·타 블로그 이미지" |

특히 이 블로그가 다루는 주제(영화·드라마·연예인·신제품)의 이미지는 대부분 배급사·소속사·제조사
저작물이다. "아이폰18 이미지를 찾아서 붙인다"는 애플 저작물 무단 사용이 되고, 네이버 블로그는
저작권 신고에 계정 단위로 대응한다.

**생성이 기본이다.** 서치는 아래 둘로 한정한다.

- **공식 보도자료 이미지** — 배포처가 언론 배포용으로 공개한 것(출처 명기 조건). `sources`에
  이미 공공/뉴스 출처를 모으고 있으므로 그 URL에서 온 이미지만 허용하면 기계적으로 통제된다.
- **라이선스 명시 무료 스톡** — Unsplash/Pexels 등. 라이선스 문구를 함께 기록할 수 있는 경우만.

"검색으로 찾은 마음에 드는 이미지"는 허용하지 않는다. 사용자가 업로드 직전 검수한다 해도
저작권 침해 여부는 눈으로 판별되지 않기 때문이다(워터마크 없는 침해 이미지가 대부분이다).

## 11. 저작권 근거를 코드로 기록

`images.copyright_status`에 출처 유형을 구조화해 남긴다. 분쟁 시 이 필드 하나로 설명할 수
있어야 한다.

```
ai-generated:chatgpt        AI 생성 (브리프 프롬프트를 metadata에 함께 보관)
press-release:<도메인>       공식 보도자료 (원 출처 URL 필수)
stock:<서비스>:<라이선스>     무료 스톡 (예: stock:unsplash:license-free)
```

이 세 형식 중 하나가 아니면 저장을 거부한다 — `copyright_status`가 비어 있거나 자유 문자열인
이미지가 섞이면 나중에 어느 것이 안전한지 가려낼 수 없다.

## 12. 저장 — 기존 `images` 테이블을 쓴다

로드맵은 `article_assets` 신설을 적어뒀지만 **원격에 이미 `images` 테이블이 있고 필요한 컬럼을
전부 갖고 있다**(`article_id`, `image_url`, `source`, `copyright_status`, `alt_text`).
2026-08-26 세션에서 발견해 `CURRENT_STATE.md`에 기록해둔 것이다. 새 테이블을 만들지 않는다.

⚠️ **첫 insert 시 확인할 것**: `images.id`가 identity(자동 증가)인지 아직 검증되지 않았다.
형제 테이블 관례로 추론만 해둔 상태다(`types/database.ts` 주석). 이번 스프린트의 첫 insert가
그 검증 지점이다.

`alt_text`는 접근성뿐 아니라 네이버 SEO에도 쓰이므로 반드시 채운다.

이미지가 손에 들어오는 시점이 사람을 거치므로(§9-1), 이번 스프린트에서 `images`에 실제로
insert하는 경로는 "사용자가 이미지 URL 또는 파일을 알려주면 기록한다"가 된다. 브리프만 만들고
끝나는 게 아니라 **결과가 DB에 남아야** Sprint 4가 집어갈 수 있다.

## 13. 이번 스프린트에서 이미지로 하는 것 / 안 하는 것

**한다**: 원고 1건에 대표 이미지 브리프 생성 → Telegram 전달 → 사용자가 ChatGPT로 확보 →
결과를 `images`에 기록(`job:image` CLI 또는 Telegram 회신).

**안 한다**: 본문 중간 배치, 여러 장, 네이버 에디터 업로드. 배치는 발행 경로(SmartEditor)가
정해지는 Sprint 4에 맞춰야 의미가 있다. 지금 배치 로직을 만들면 Sprint 4에서 버릴 가능성이 높다.

Telegraph 미리보기에 이미지를 넣는 것도 이번에는 하지 않는다 — Telegraph에 이미지를 실으려면
별도 업로드 API를 거쳐야 하는데, 어차피 최종 목적지는 네이버다. 사용자가 ChatGPT에서 이미지를
직접 보고 있으므로 Telegraph에서 한 번 더 볼 실익이 없다.

## 16. 이번 스프린트가 끝나면

원고가 자동 검수를 거쳐 검수 결과와 함께 도착하고, 버튼 한 번으로 `approved` 상태가 된다.
이미지 브리프가 함께 오고, 사용자가 확보한 이미지가 `images`에 기록된다. 그러면 Sprint 4
(네이버 임시저장)가 집어갈 입력이 완성된다 — 승인된 원고 + 제목 + 해시태그 + 이미지.
