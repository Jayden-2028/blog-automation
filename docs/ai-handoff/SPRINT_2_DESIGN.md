# Sprint 2 설계안 — 자료조사 + 원고 생성

작성일: 2026-08-27 · 상태: **1~10절 구현 완료, 첫 원고 실측 완료** (12~13절은 후속 과제, 미착수)

## 1. 목표

`article_jobs`에 `status='selected'`로 쌓인 job을 읽어 **출처가 붙은 원고 초안**까지 만든다.
이미지·검수·발행은 Sprint 3~4다.

### 완료 조건

1. 선택된 job 1건이 자료조사를 거쳐 `sources`에 근거 N건을 **출처 등급과 함께** 남긴다
2. 그 근거를 입력으로 원고가 생성되어 `articles`에 저장된다
3. job 상태가 `selected → researching → writing → review`로 전이된다
4. 의학 주제는 **사람 교차확인 대기** 상태로 따로 표시된다
5. 원고 1건당 소요 시간과 비용이 실측된다

현재 `selected` 상태 job이 4건 있어 실데이터로 바로 검증할 수 있다.

## 2. ⚠️ 설계 전제가 하나 깨졌다 (2026-08-27 실측)

로드맵과 `runHeadlessClaude.ts` 주석은 **"기존 블로그 작성 스킬을 헤드리스에서 그대로
재사용한다"**를 전제로 했다. 실제로 확인해보니 아니었다.

```
$ claude -p --allowed-tools Skill  (스킬 목록 질의)

anthropic-skills:entertainment-blog-writer   없음
anthropic-skills:parenting-blog-writer       없음
anthropic-skills:trend-blog-writer           없음
moai-marketer:content-blog                   있음
moai-writer:korean-humanize                  있음
moai-coworker:ai-slop-reviewer               없음
```

`anthropic-skills:*`는 대화형 세션에만 있고 **헤드리스 CLI에서는 로드되지 않는다.**

**대체재가 더 잘 맞는다.** `moai-marketer:content-blog`는 네이버 블로그를 명시적으로 다루고 SEO
메타까지 만든다. 카테고리별로 스킬이 갈리지 않아 분기도 단순해진다. `moai-writer:korean-humanize`를
후처리로 체이닝한다. `runHeadlessClaude.ts` 상단의 낡은 주석도 함께 고쳐야 한다.

## 3. 데이터 연결 — `job_id` 컬럼 추가

`sources`와 `articles`는 `keyword_id`(int, `keywords.id` 참조)로 설계돼 있는데, **우리 파이프라인은
`keywords` 테이블에 아무것도 쓰지 않는다.** 그래서 `keyword_id`는 항상 null이 되어 원고를 job과 이을
방법이 없다.

```sql
alter table public.sources  add column if not exists job_id uuid;
alter table public.sources  add column if not exists authority text;
alter table public.articles add column if not exists job_id uuid;

create index if not exists idx_sources_job_id  on public.sources (job_id);
create index if not exists idx_articles_job_id on public.articles (job_id);
```

`keyword_id`는 건드리지 않는다(기존 testCrud 데이터 2건이 쓰고 있다). FK 제약은 걸지 않는다 —
`article_jobs`가 정리돼도 원고는 남아야 하고, 이는 `article_jobs`가 `keyword_rankings`를 참조하지
않고 값을 복사한 것과 같은 판단이다.

`article_jobs.metadata`에 원고를 넣는 방안도 검토했으나, 본문이 5~10KB라 jsonb에 넣으면 job 조회가
매번 무거워진다.

## 4. 자료조사 — 출처 등급이 핵심이다

### 4-1. 왜 등급이 필요한가 (2026-08-27 실측)

같은 파이프라인인데 **주제에 따라 근거 품질이 완전히 다르다.**

`"2026 근로장려금 지급일"` 웹문서 검색:
```
🏛 hometax.go.kr    국세청 홈택스 - 근로·자녀장려금     ← 1차 출처
🏛 hometax.go.kr    국세청 홈택스
🏛 awoo.or.kr       자녀장려금 2026 지급일...
→ 공공 9건 / 일반 1건
```

`"아기 셔더링어택 증상"` 웹문서 검색:
```
   in.naver.com    셔더링어택 영아연축증상 차이점 대처법
   in.naver.com    이거 아기 셔더링어택 맞나요?
   clien.net       아기가 부르르떠는 경련 증상이 있네여 ㅠ,ㅠ
→ 공공 0건 / 뉴스 0건 (전부 블로그·커뮤니티)
```

정책·지원금은 정부 공식 사이트가 잘 잡히고, **의학 주제는 하나도 안 잡힌다.** 이 차이를 무시하고
같은 파이프라인에 태우면, 영아 경련 감별 같은 주제를 커뮤니티 게시글 근거로 쓰게 된다.

### 4-2. 출처 등급 분류

수집 시 도메인으로 자동 판정해 `sources.authority`에 저장한다.

| 등급 | 판정 | 예 |
|---|---|---|
| `official` | `.go.kr` / `.or.kr` / `.re.kr` | hometax.go.kr, 복지로 |
| `medical` | 병원·의학회 도메인 화이트리스트 | amc.seoul.kr, snuh.org |
| `news` | 뉴스 API 결과 | wikitree.co.kr, etoday.co.kr |
| `community` | 그 외(블로그·카페·커뮤니티) | in.naver.com, clien.net |

`community`도 **버리지 않는다.** 의학 주제에서는 그게 유일한 근거이고, 실제 양육자들이 무엇을
궁금해하는지가 담겨 있어 글의 구성에 쓸모가 있다. 다만 **등급을 원고 프롬프트와 검수에 그대로
노출**해서, 어떤 주장이 어느 등급에 기대고 있는지 드러나게 한다.

### 4-3. 공공 도메인에 한해 본문을 읽는다

`official` 등급 URL은 **화이트리스트 도메인에 한해** WebFetch로 본문을 가져온다. `hometax.go.kr`이
잡히는데 스니펫만 쓰는 건 아깝다.

도메인이 제한돼 있어 **어떤 URL을 읽었는지 `sources`에 그대로 남고 감사 가능성이 유지된다.**
그 외 등급은 검색 API 스니펫만 쓴다.

### 4-4. 언론사·블로그 본문은 긁지 않는다 (검토 후 기각)

- **저작권** — 기사 본문 수집·저장은 로드맵 §6-1의 위험 범위다. 검색 API 스니펫은 네이버가 그
  용도로 제공하는 것이라 성격이 다르다
- **취약성** — 사이트마다 마크업이 다르고 수시로 바뀐다
- **ToS** — 대부분이 자동 수집을 금지한다

정부 사이트는 공공누리 등으로 이용 조건이 열려 있어 다르게 취급한다.

## 5. 의학 주제 — 생성은 하되 사람이 교차확인한다

### 5-1. 판정

키워드·headline의 어휘로 판정한다(`config/keywordCategoryRules.ts`와 같은 방식, 순수 함수 + 테스트).

```
증상, 진단, 치료, 처방, 부작용, 복용, 접종, 예방접종, 발열, 경련, 발진,
연축, 아토피, 수족구, 장염, 중이염, 황달, 탈수, 응급, 골절, 통증 ...
```

보수적으로 잡는다 — **의학이 아닌데 의학으로 분류되는 쪽이, 의학인데 놓치는 쪽보다 낫다.**

### 5-2. 의학 주제일 때 달라지는 것

**① 원고를 만든다.** 배제하지 않는다. 블로그·커뮤니티 근거도 그대로 쓴다.

**② 프롬프트가 달라진다.**
- 진단·처방으로 읽힐 표현 금지 (`~이면 ~입니다`, `~하면 낫습니다`)
- 개별 사례 소개는 출처를 명시하고 일반화하지 않는다
- 본문에 전문가 상담 안내를 반드시 포함
- 응급 신호(경련 지속, 의식 저하 등)는 즉시 진료 안내를 앞쪽에 배치

**③ `metadata.requiresMedicalReview = true`로 표시**하고 status는 `review`에 머문다.
Sprint 3의 자동 검수를 통과해도 **이 표시가 있으면 사람 승인 없이는 다음 단계로 못 간다.**

**④ 텔레그램 알림이 다르다.** 일반 원고는 "검수 요청"이지만, 의학 주제는:

```
⚕️ 의학 주제 — 직접 확인이 필요합니다

아기 셔더링어택 증상 원인 언제

이 원고의 근거는 전부 community 등급입니다 (공공 0건 / 의료 0건).
아래 출처를 직접 확인하신 뒤 승인해주세요.

1. [community] 셔더링어택 영아연축증상 차이점 — https://in.naver.com/...
2. [community] 아기가 부르르떠는 경련 증상 — https://clien.net/...

[✅ 확인함]  [✏️ 수정 필요]  [🗑 폐기]
```

출처 URL을 **전부 나열**해서 클릭 한 번으로 원문을 볼 수 있게 한다. 교차확인을 요청하면서
확인할 대상을 안 주면 형식적인 승인이 된다.

### 5-3. 비-의학 주제의 근거 부족

의학이 아니어도 근거가 얇을 수 있다. 이때는 **거부하지 않고 경고만** 붙인다.

| 유형 | 기대 등급 | 미달 시 |
|---|---|---|
| 정책·지원금 | `official` 1건 이상 | 알림에 ⚠️ 표시, 진행 |
| 의학 | `official`/`medical` 1건 이상 | **사람 교차확인 필수**(§5-2) |
| 연예·드라마 | `news` 1건 이상 | 알림에 ⚠️ 표시, 진행 |

정책에서 공공 출처가 없는 건 실측상 드물다(9/10이 공공이었다). 드물게 발생하면 사람이 보고
판단하면 된다.

## 6. 파이프라인

```
runArticleJob(jobId)
 1. job 조회 (status='selected' 확인)
 2. status -> 'researching'
 3. NAVER 검색 재조회(뉴스/웹/블로그) -> 도메인으로 authority 판정 -> sources 저장
 4. official 등급 URL은 화이트리스트 도메인에 한해 본문 fetch -> sources.content 보강
 5. 의학 주제 판정 -> metadata.isMedical
 6. 팩트 카드 조립 (등급·출처·발행일·본문/스니펫 + URL)
 7. status -> 'writing'
 8. claude -p (content-blog + korean-humanize, 의학이면 프롬프트 강화) -> 원고
 9. articles에 job_id로 저장 (ai_model 기록)
10. status -> 'review', 의학이면 metadata.requiresMedicalReview = true
11. 텔레그램 알림 (의학이면 출처 목록 포함 교차확인 요청)
```

**단계마다 status를 전이시키는 이유**: 어디서 멈췄는지 DB만 보고 알 수 있어야 한다. Sprint 0에서
파이프라인이 조용히 죽었을 때 로그를 열어보고서야 알았던 문제를 반복하지 않는다.

**실패 처리**: status를 되돌리지 않고 `metadata.lastError`에 사유를 남긴다. `researching`에서 멈춘
job은 다시 돌릴 수 있어야 하므로 status는 그대로 둔다.

## 7. 모든 원고에 강제할 규칙

로드맵 §6-2·§6-4의 위험을 프롬프트에서 막는다. Sprint 3 검수가 2차 방어선이다.

1. **제공된 근거를 벗어난 수치·날짜·인용을 만들지 않는다**
2. **인물 관련은 확정 보도된 사실만.** 추측성 표현(`~라는 의혹`, `~한 듯`) 금지 — 한국은 사실을
   적시해도 명예훼손이 성립할 수 있다(형법 307조 1항)
3. **정책·지원금은 출처 URL과 발표일을 본문에 명시**하고 "작성 시점" 기준임을 밝힌다
4. **`community` 등급에만 기댄 주장은 단정하지 않는다** — "~라고 알려져 있습니다" 수준으로 낮추고
   출처를 함께 밝힌다
5. 과장된 낚시 표현(충격, 경악, 소름) 금지
6. 본문 끝에 참고 출처 목록(제목 + URL + 등급)

## 10. 남은 결정 항목

**① 원고 생성을 자동으로 돌릴까, 수동 트리거로 둘까?**
수동(`npm run job:write -- <jobId>`)을 제안한다. **비용이 실측되기 전에 무인 자동화는 위험하다.**

**② 원고 길이 목표**
네이버 블로그 기준 1,500~2,500자를 제안한다. 짧으면 저품질 판정 위험, 길면 비용과 이탈률이 는다.

**③ 의료 도메인 화이트리스트 범위**
서울아산·서울대병원·질병관리청 정도로 시작하고 필요할 때 넓히는 것을 제안한다.

## 12. 첫 실측에서 드러난 결함과 후속 과제 (2026-08-27)

"2026 경복궁 별빛야행" job으로 첫 원고를 실제 생성(조사 2초 / 작성 185초 / 본문 1,786자)한 뒤
결과를 역추적해 확인한 것들이다.

### 12-1. 잘 동작한 것

프롬프트 안전 규칙은 의도대로 작동했다. 원고의 구체 사실(가격 60,000원, 문의 1522-2295,
주소 사직로 161, 12첩 반상, 탐방로 계조당→외소주방→집옥재→향원정, 기간 2026.09.02~10.24)은
전부 수집된 official 출처에 실제로 존재하는 값이었다. 근거에 없는 예매 오픈 날짜에 대해서는
모델이 단정하지 않고 "공식 채널 공지를 기준으로 삼으세요"로 처리했다 - §7-1 규칙이 지켜졌다.

### 12-2. 결함 A — 공공 페이지에서 네비게이션만 긁어온다

`kh.or.kr` 3건의 수집 본문 3,000자가 전부 메뉴 텍스트였다.

```
[official] 2026년 경복궁 별빛야행 (3,000자)
실제 내용: " 경복궁 / 창덕궁 / 덕수궁 / 창경궁 / 종묘 / 수문장 교대의식 ..."
```

`extractReadableText`가 `root.text`를 그대로 쓰고 앞 3,000자를 자르는데, 그 구간이 네비게이션이다.
쓸 만한 사실은 사실상 `visitkorea` 1건에서만 나왔다. 그런데 알림에는 "공공 4건"으로 표시되어
**근거 충실도를 실제보다 과대평가**하게 만든다.

수정 방향: `<main>`/`<article>` 우선 선택, `<nav>`/`<header>`/`<footer>`/`<aside>` 제거, 단순
앞부분 자르기 대신 의미 있는 구간 선택.

### 12-3. 결함 B — 빈약한 fetch 결과가 스니펫을 덮어쓴다

`enrichOfficialSources`는 official 등급이면 검색 스니펫을 fetch 본문으로 **교체**한다. fetch
결과가 메뉴 쓰레기여도 교체하므로, 원래 스니펫에 있던 정보가 오히려 사라진다.

수정 방향: fetch 결과가 스니펫보다 명백히 나을 때만 교체한다(길이·의미 있는 문장 비율 기준).

### 12-4. 결함 C — 예매 정보가 있는 페이지를 읽을 수 없다

핵심 정보(예매 오픈일)가 있는 `ticketlink.co.kr`은 **JavaScript SPA**라 HTTP fetch로는 읽히지
않는다. 실측: HTTP 200에 추출 텍스트 29자(제목만), "응모기간"/"당첨발표" 모두 없음.

즉 §4-3의 "official 도메인만 fetch" 정책을 티켓 도메인까지 넓혀도 **그대로는 해결되지 않는다.**
SPA를 읽으려면 Playwright 렌더링이 필요하다(Creator Advisor에서 쓰는 것과 같은 방식).

## 13. 키워드 밸류에이션 문제 (신규 과제)

### 13-1. 무엇이 문제인가

실제 티켓링크 페이지를 사람이 확인한 결과:

```
응모기간 : 2026.08.14(금) 14:00 ~ 08.20(목) 14:00   ← 이미 마감
당첨발표 : 2026.08.24(월) 17:00                      ← 이미 발표
오늘     : 2026.08.27
```

**이 키워드는 검색량은 높지만 포스팅 가치가 거의 없다.** 예매가 끝나서 독자가 글을 읽고 할 수 있는
행동이 없다. 검색량이 오른 이유도 신규 관심이 아니라 **기응모자들의 당첨 확인 트래픽**으로 추정된다.

이건 원고 품질 문제가 아니라 **키워드 선별 단계의 문제**다. 잘 쓰인 원고라도 대상 키워드가
"이미 끝난 이벤트"면 유입도 체류도 기대할 수 없다.

### 13-2. 왜 지금 구조로는 못 잡는가

- 키워드 자체(`2026 경복궁 별빛야행 야간개장 예약 예매방법 가격 수라상`)에 "당첨발표" 같은
  사후 신호 어휘가 없다 - 어휘 규칙으로는 안 잡힌다
- 수집된 근거에 있는 날짜는 **행사 기간**(09.02~10.24, 아직 시작 전)이라 "만료"로 보이지 않는다.
  마감된 것은 **응모 기간**인데 그 정보가 SPA 안에 있어 수집되지 않았다
- 6-factor 스코어링은 검색량·신선도를 보지 **행동 가능성(actionability)을 보지 않는다**

### 13-3. 해결 방향 (검토 필요, 아직 결정 아님)

**① 사전 확인 체크포인트 (가장 싸고 넓게 듣는다)**
자료조사만 먼저 하고 팩트 카드 요약을 Telegram으로 보내 "이대로 쓸까요?"를 묻는다. 사용자가
보고 아니면 중단한다. 원고 생성 전에 막으므로 **3분 + LLM 비용을 아낀다**. 이미 수동 트리거
파이프라인이라 흐름상 자연스럽다. 만료뿐 아니라 "근거가 부실하다", "주제가 안 맞는다" 같은
모든 종류의 문제를 사람이 한 번에 거른다.

**② 행동 마감일 자동 감지**
수집된 텍스트에서 `응모기간`/`접수기간`/`신청기간`/`예매기간`/`마감` 뒤의 날짜를 뽑아 오늘과
비교한다. 지났으면 job에 `actionabilityExpired`를 표시하고 원고 생성 전에 중단한다.
다만 12-4 때문에 **핵심 페이지가 SPA면 이 데이터를 못 얻는다** - ③과 함께여야 실효가 있다.

**③ 예매/신청 페이지에 한해 Playwright 렌더링**
키워드에 행동 어휘(예매·신청·접수·응모)가 있을 때만, 티켓/신청 도메인을 Playwright로 렌더링해
읽는다. Creator Advisor에서 쓰는 것과 같은 방식이고 이미 설치돼 있다. 비용은 job당 5~10초.
수동 파이프라인(하루 1~2건)에서는 감당할 만하다.

**④ 선별 단계로 되먹임 (장기)**
`article_jobs`에 쌓이는 `rejected` + `actionabilityExpired` 이력을 모아 어떤 키워드 패턴이
가치가 낮은지 학습한다. 지금은 데이터가 부족하다(rejected 6건). Sprint 1에서 Pass를 기록으로
남기기로 한 결정이 여기서 쓰인다.

**⑤ 스코어링에 actionability 반영 (승인 게이트)**
6-factor에 "행동 가능성" 축을 추가하는 방안. 다만 scoring 변경은 `CLAUDE.md`상 승인이 필요하고,
④의 데이터가 쌓이기 전에는 근거 없이 가중치를 정하게 되므로 지금은 이르다.

### 13-4. 권고

**①을 먼저 넣는다.** 구현이 가장 가볍고, 만료 케이스뿐 아니라 근거 부실·주제 부적합까지 전부
사람이 한 번에 거른다. ②③은 ①이 반복적으로 같은 이유로 중단될 때 자동화하면 된다 - 자동
감지를 먼저 만들면 어떤 패턴을 감지해야 하는지 모른 채 규칙을 추측하게 된다.

## 14. 구현 완료 (2026-08-27, 사용자 "1~4번 모두 제안대로 진행해줘" 승인)

12절·13절에서 식별한 문제 중 아래 세 가지를 구현하고 회귀 테스트로 고정했다. 커밋:
`e1b953d`(결함 A/B), `8f7540b`(체크포인트 + Telegraph).

### 14-1. 결함 A/B 수정 (12-2, 12-3)

`fetchOfficialSourceContent.ts`를 `<main>`/`<article>`/`#content` 등 선택자 우선 추출 +
`<nav>`/`<header>`/`<footer>`/`<aside>` 등 chrome 제거 + 산문 비율 휴리스틱(`looksLikeProse`)으로
재작성했다. fetch 결과가 스니펫보다 명백히 나을 때만 교체한다(`shouldReplaceSnippet`).

**실측 검증**: 같은 `kh.or.kr` URL을 재수집한 결과 "예매기간 2026-08-14 ~ 2026-08-20", "예매권
추첨 응모", "당첨자 발표" 문구가 정상 추출됨을 확인했다 - 애초에 사용자가 지적한 "예매 시작일이
빠져 있다"는 문제의 직접 원인이었다. 12-4(SPA 페이지, ticketlink.co.kr)와는 별개 문제였고, 그쪽은
여전히 미해결이다(아래 14-4).

### 14-2. 사전 확인 체크포인트 (13-3 ①, 13-4 권고 채택)

`runArticleJob`을 `runResearchStage` + `runWritingStage`로 분리하고 CLI 3개를 추가했다.

```
npm run job:research -- <jobId>   조사만 하고 팩트 카드를 Telegram으로 보낸다
(사람이 확인)
npm run job:write -- <jobId>      저장된 근거를 재사용해 바로 작성한다 (재조사 안 함)
npm run job:reject -- <jobId>     가치가 없다고 판단되면 여기서 끝낸다 (사유 + 중단 시점 기록)
```

`job:reject`는 `rejectedReason`/`rejectedVia`/`rejectedAt`/`rejectedAtStatus`를 job metadata에
남긴다 - 13-3 ④(선별 단계로 되먹임)를 위한 데이터 축적이 지금부터 시작된다.
`job:write`를 jobId 없이 실행하면 `researching`(조사 완료, 작성 대기)과 `selected`(조사 전)
job을 구분해서 보여준다.

**미리보기 형식 재실측 (같은 날, 경복궁 별빛야행 job 재실행 중 2차 피드백)**: 첫 버전은 출처별
제목+150자 발췌+URL을 그대로 나열했는데, 실제로 보니 여러 출처가 네비게이션 메뉴 텍스트로
시작해 있어 링크를 일일이 열어봐야 판단할 수 있었다("웹페이지 긁어온 형태"). 신규
`summarizeResearchForReview()`가 근거 전체를 헤드리스 Claude에 넘겨 요약을 만들게 했다(제목
생성과 비슷한 비용, 실측 20~30초). 프롬프트를 두 번 다듬었다:

1. 서술형 문장 → 처음엔 자연스러웠지만 모델이 "근거 4에서 확인" 같은 출처 번호를 언급했다
   (그 번호는 미리보기에 더 이상 안 보이는데도)
2. "라벨: 내용" 나열형 → 가독성은 좋아졌지만 "이 키워드가 원고로 쓸 가치가 있는지"에 대한
   편집 판단이 사라졌다(예: 우선 예매는 마감돼도 잔여석 선착순 예매와 행사 자체가 아직 남아
   "잔여석 안내/후기" 각도로는 가치가 있다는 판단)
3. **최종**: `[⚠️ 경고(있을 때만)] → 빈 줄 → [불릿(-) 사실: 일정/가격/신청/대상/장소/유의] →
   빈 줄 → [판단: 한 줄]`. "판단:" 줄을 필수로 만들어, 마감된 이벤트라도 다른 각도로 가치가
   남아 있으면 그걸 짚고 완전히 끝났으면 그것도 명시하게 했다.

요약 생성이 실패하면(네트워크 등) 기존 출처 나열 방식으로 폴백한다 - 판단 재료가 아예 없는
것보다는 낫다.

### 14-3. Telegraph 원고 보기 (사용자 4번째 질문 대응)

Telegram `parse_mode=HTML`은 원고의 마크다운(`##`, `**`)을 서식으로 렌더링하지 않고 글자
그대로 보여준다. `src/services/telegraph/`를 신규 도입해 원고를 telegra.ph 페이지로 발행하고,
Telegram 알림에는 "📄 원고 보기" URL 버튼만 단다. 발행이 실패하면(네트워크 등) 기존 본문
dump 방식으로 자동 폴백한다 - Telegraph는 부가 기능이지 원고 확인의 필수 경로가 아니다.

**실측 검증**: 실제 "2026 경복궁 별빛야행" 원고를 발행해
`https://telegra.ph/2026-경복궁-별빛야행-9월-야간개장-예약예매방법가격수라상-정리-08-27`로
확인, `<h3>`/`<a href>` 렌더링을 curl로 검증했다.

⚠️ **트레이드오프 (사용자 승인)**: Telegraph 페이지는 URL을 아는 누구나 볼 수 있는 공개 페이지다
(비공개 아님). 사람 검수 전인 원고도 이 URL로 새어나갈 수 있다. 발행마다 임시 계정을 새로
만들어 쓰므로(access_token 영구 보관 없음) 이번 스프린트에서는 발행 후 수정이 불가능하다.
