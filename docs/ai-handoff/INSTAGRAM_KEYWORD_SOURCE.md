# 인스타그램 기반 키워드 수집 — 인수인계

> **이 문서만 읽으면 이어서 작업할 수 있다.** 2026-09-21 시작, 별도 세션으로 분리.
> 작업 위치: `~/blog-automation/ig-dev` (브랜치 `feat/instagram-keyword-source`)

## 왜 이걸 만드는가

사용자 판단(2026-09-21): 현재 키워드 수집이 수익화 관점에서 약하다.

- 조회수 편차가 극단적이다 — 국중박 분장놀이 **1,500회**, 김민희 50회, 나머지는 전부 10회 미만.
- 원인 진단: 이미 화제가 된 **뒤에** 수집된다. 독자가 검색을 시작한 시점보다 늦다.

그래서 수집 **소스**를 네이버·트렌드에서 **인스타그램 이슈 페이지**로 바꾼다. 소셜에서 막
퍼지기 시작한 시점을 잡는 것이 목적이다.

## 사용자가 이미 결정한 것 (재논의 금지)

| 항목 | 결정 |
|---|---|
| 기존 파이프라인 | **그대로 운영.** 데모가 완벽하다고 판단될 때만 교체 |
| 개발 격리 | 별도 워크트리. DB·마이그레이션 손대지 않음 |
| 순위 기준 | 소셜 반응으로 후보 선별 → 네이버 블로그 포화도로 재정렬 |
| 카테고리 | **라벨만.** 카테고리별 순위를 매기지 않는다 |
| 주기 | 데일리, 주제 무관 일괄 |
| 산출물 | HTML 페이지 (텔레그램 아님) |
| 소스 목록 | 한 번에 받아 고정 (`src/config/instagramSources.ts`, 15개) |
| 비용 | **무료 수단만.** 유료 스크래핑 서비스 금지 |

## 기술 판단과 그 근거

### 데이터 수집: Meta Business Discovery API

무료로 인스타 데이터를 안정적으로 얻는 길은 이것뿐이다.

```
GET /{내-IG-비즈니스-계정-ID}
    ?fields=business_discovery.username(TARGET){followers_count,media_count,media{...}}
```

**로그인 세션 크롤링은 검토 후 기각했다.** 이 프로젝트가 티스토리를 접은 이유와 같은 실패를
반복한다(세션이 계속 풀려 사람이 매번 개입). 인스타는 봇 탐지가 더 공격적이고 계정 정지
위험까지 붙는다. RSS 브리지·미러 사이트는 대부분 죽었다.

### 못 가져오는 것 — 설계에 못박아 둘 것

```
가능   좋아요, 댓글 수, 게시 시각, 캡션, 미디어 유형, 팔로워 수, 게시물 수
불가   저장수, 공유수, 도달, 노출, 시청 지속률(retention)
```

**retention과 저장수는 자기 계정 인사이트 전용이다.** 남의 페이지에서는 어떤 방법으로도 못
얻는다. 사용자가 초기에 "engagement와 retention 기준"을 언급했지만 retention은 불가능하다고
보고했고 수용됐다. 점수는 **좋아요·댓글·시각·캡션 네 가지로만** 짜야 한다.

### 점수 설계 (`scoreInstagramTopics.ts`)

페이지마다 팔로워·게시 빈도가 달라서 정규화가 필요하다. 다음 판단이 핵심이다.

1. **팔로워로 나누지 않는다.** 흔한 방식이지만 작은 계정을 구조적으로 과대평가한다(팔로워가
   적을수록 참여율이 높게 나온다). 대신 **그 계정 자신의 최근 중앙값 대비 배수**를 쓴다.
2. **평균이 아니라 중앙값.** 대박 한 건이 기준선을 끌어올리면 그 페이지의 다음 대박을 못 잡는다.
3. **팔로워는 log10 도달 보정으로만** 다시 넣는다. 같은 배수면 큰 페이지가 이겨야 한다.
4. **댓글 가중치 3배.** 좋아요는 반사적이지만 댓글은 비용이 들고, "이게 무슨 일이야?" 같은
   댓글은 검색 의도의 직접 신호다.
5. **교차 등장이 가장 강한 신호.** 단, 보너스는 게시물 수가 아니라 **서로 다른 페이지 수**로
   준다 — 한 페이지가 같은 주제로 3건 올린 걸 3배로 치면 안 된다.
6. **마지막에 블로그 포화도로 보정.** 인스타 반응은 구글 디스커버를 잘 예측하지만 검색 수요는
   예측하지 못한다(밈·감성 짤은 반응만 좋다). 조회 실패(null)가 소셜 신호를 소멸시키지 않도록
   가중치를 제한했다.

불변식 10개가 `npm run test:ig-score`로 고정돼 있다. **이 테스트를 깨는 변경은 설계 변경이다.**

### fixture 실행 결과 (설계 검증됨)

게시물 12건 → 주제 4건. 광고·이벤트·날씨·감성 사진은 제외됐다.

```
1. 국중박 분장놀이 결선 25팀 공개   81.0  3개 페이지 · 평소의 12.9배 · 블로그 1,190건
2. 지창욱 성형 논란               36.8  2개 페이지 · 평소의 15.3배 · 블로그 161건
3. 서울 지하철 요금 인상안 재논의    3.2  단일 페이지 · 평소의 5.0배 · 블로그 129,471건
4. 퍼니셔 원 라스트 킬 공개일        1.9
```

3위가 의미 있다 — 반응은 5배로 좋았지만 블로그 글이 12.9만 건이라 기회도가 깎였다.
**소셜 반응만 보면 안 되는 이유**가 이 한 줄로 드러난다.

## 막혀 있는 것

**Meta 기기 인증.** 사용자가 페이스북 설정을 바꾸려 하자 "평소에 사용하지 않는 기기" 잠금이
걸렸다. 보통 24시간, 해당 기기를 평소처럼 써야 풀린다. 이게 풀려야 토큰이 나온다.

토큰이 준비되면 `.env`에 두 값이 들어온다(사용자가 직접 넣는다 — **값을 출력하지 말 것**).

```
IG_ACCESS_TOKEN=     시스템 사용자 토큰(만료 없음) 권장
IG_USER_ID=          내 인스타그램 비즈니스 계정 ID
```

> ⚠️ 기본 토큰은 1시간, 장기 토큰도 60일이면 만료된다. 매일 도는 파이프라인이라 **Meta Business
> Suite의 시스템 사용자 토큰**을 써야 한다. 안 그러면 두 달 뒤 같은 문제로 멈춘다(Blogger
> refresh token 때와 같은 구조).

## 다음 단계

1. **`npm run ig:probe`** — 여기서 막히면 설계가 통째로 바뀐다. 확인 항목:
   - 15개 중 몇 개가 비즈니스 계정인가(개인 계정은 조회 불가 → 목록에서 제외)
   - 최근 48시간 게시물 합계 — **60건 미만이면 페이지를 더 받아야 한다**
   - 중앙값 계산에 필요한 과거 30건이 확보되는가
   - 릴스 조회수가 오는가(오면 점수에 추가 검토)
2. probe 결과를 `instagramSources.ts`의 `reachable` 필드에 기록
3. **`npm run ig:collect`** 실제 데이터로 실행 → HTML 확인
4. 사용자와 결과 검토 → 가중치 조정(`SCORING` 상수)
5. 완벽 판정 후 교체 설계 (스케줄러·알림 연결, DB 테이블 여부)

## 열려 있는 질문

- **후보 풀 크기.** 이슈 페이지는 하루 1~3건이 흔해서 15개 × 2일 = 60~90건 예상. 중복을 묶으면
  독립 주제는 30~50개. top 20을 뽑기에 빠듯하다. 부족하면 URL 추가 요청.
- **검색량 축.** 지금은 블로그 포화도만 쓰고 수요 신호는 중립값(0.5) 고정이다. 네이버 DataLab
  검색량을 실제로 붙일지는 probe 이후 판단.
- **교체 시점의 기존 파이프라인 처리.** 병행 운영할지 즉시 교체할지 미정.

## 절대 하지 말 것

- `prod` 워크트리와 `main` 브랜치를 건드리지 않는다. 운영이 계속 돌아야 한다.
- 마이그레이션·원격 DB 쓰기 금지(승인 게이트). 데모 단계는 로컬 파일로 충분하다.
- `.env` 값을 읽거나 출력하지 않는다.
- 유료 스크래핑 서비스를 제안하지 않는다.
