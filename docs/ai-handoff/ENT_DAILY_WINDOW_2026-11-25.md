# 엔터 키워드 수집 — 하루 창 (2026-11-25)

상태: 코드 완료(브랜치 `feat/ent-daily-window`), **운영 미배포**. 라이브 NAVER 호출 없이 오프라인 테스트로만 검증했다.

## 왜

엔터 수집(`entertainment-keyword.yml`, 18:00 KST 1회)은 검색어마다 NAVER 뉴스·블로그·웹을 **최신순 10건**만 받았다.
"캐스팅" 같은 넓은 검색어는 18시 직전 몇 분치 기사만 잡았고, 그날 오전·오후의 공개일 확정·캐스팅·예고편 기사를
놓쳤다(수지 '현혹' 공개일 확정은 Top 10 탈락, '천천히 강렬하게' 예고편 공개는 수집 0건). 점수도 freshness
(반감기 12h)·newsVelocity(15건 만점)가 "18시 기준 최신"에 기울어 있었다.

사용자 지시: "키워드 수집 텀을 데일리로. 18시 직전 10분보다 그날 하루 종일 가장 이슈가 되었던 뉴스를 찾자.
블로그 포스팅은 22시~새벽 1시라 그 시간대 최신성은 의미가 없다."

## 무엇이 바뀌었나 (엔터 경로만)

| 항목 | 전 | 후 |
|---|---|---|
| 뉴스 | 검색어당 최신 10건 | 최근 24h 창이 찰 때까지 `start=1,101,201`·`display=100`·`sort=date`, 검색어당 **300건** 상한 |
| 블로그 | 최신 10건 | 같은 방식, 검색어당 **100건** 상한(postdate가 날짜뿐이라 창은 KST 날짜 단위 = 18시 실행이면 어제 0시부터) |
| 웹문서 | 10건 | 그대로 10건(날짜 없음) |
| 창 밖 문서 | - | 만나면 그 검색어 중단. 단 **앞 10건(기존 수집분)은 창 밖이어도 남긴다** - 7일 컷이 그 10건의 바깥 한도 |
| 호출 상한 | - | 뉴스+블로그 1회 실행 **500회**. 첫 페이지(검색어×2)는 항상 보장, 추가 페이지만 예산 안에서 |
| freshness | 0h부터 반감기 12h | **창(24h) 안 만점 15**, 창 밖부터 반감기 12h, 창+48h(=72h)에 0 |
| newsVelocity | cap 15, 24h 안 x1 / 밖 x0.6 | **cap 30**, "창 안 x1 / 창 밖 x0.6"(기준 시각을 창에 묶음) |
| 진단 로그 | - | `[점수진단]` 상위 50개: 6개 항목 점수 + 기사·블로그·웹 수 + 첫/마지막 기사 시각(DB 저장 없음) |

가중치(합 100)와 trendMomentum·contentDemand·crossSource·clickPotential은 그대로다. 점수 곡선은
`scoreKeyword(..., { profile })`로 엔터 경로에서만 넘어가고, 사회·사용설명서·`runKeywordRanking`·자료조사 수집은
기존 그대로다(`collectSourcesForJob`은 `dailyWindow`를 넘기지 않는다).

newsVelocity cap 30은 **실측이 아니라 추정**이다(키 없는 오프라인 작업). 근거와 재보정 방법은
`src/config/keywordScoring.ts` 하루 창 프로필 주석. 운영 첫 주 `[점수진단]` 로그로 묶음 기사 수 분포를 보고 맞춘다.

## 처리량

- NAVER 호출: 전 ~3×시드(시드 ~65개면 ~195회) → 최악 `65×2(첫 쪽) + 65×2(뉴스 추가 2쪽) + 65(웹) = 325회`.
  상한 500은 평소엔 닿지 않는 안전판이다. 일 25,000회 한도 대비 여유 크다.
- 문서 수: 전 ~1,300건 → 추정 수천~1만 건(넓은 시드가 300건씩 찬다). 실제 값은 `ℹ️ [collectNaverCandidates] 하루 창` 로그.
- clustering은 O(n²)라 그대로 두면 1만 건에서 수 분이었다. **결과를 바꾸지 않는 최적화**를 넣었다
  (char n-gram을 문서당 한 번만 만들고, 신뢰하지 않는 쌍은 계산 생략). 옛 구현과 2,500건 합성 데이터에서
  결과 동일·21배 빠름을 확인했다. 맥 기준 최악(전부 다른 제목 12,000건) clustering 10.5초 + 주제 병합 preview 12.7초.
- LLM 호출: 변화 없음 - 주제어 추출은 상위 60건 1회, 경쟁도 프로브 60회도 그대로(문서 수와 무관).
- 워크플로 timeout 15분은 그대로 둔다.

## 롤백·조절 (repo variable, 코드 변경 없음)

- `ENT_NAVER_WINDOW_HOURS=0` → 하루 창 전체(페이지네이션·점수 프로필·진단 로그)가 꺼지고 옛 동작.
- `ENT_NAVER_MAX_NEWS_PER_QUERY` / `ENT_NAVER_MAX_BLOG_PER_QUERY` / `ENT_NAVER_MAX_CALLS`로 상한 조절.

## 남은 위험

- **clustering이 같은 사안을 잘게 쪼갠다**(Top 10 related_count 30일 평균 1.1~2.0). 묶음 토큰 집합이
  멤버 합집합이라 묶음이 커질수록 새 기사의 Jaccard가 낮아진다. 하루 창에서 기사가 늘면 "하루 기사 수"가
  한 묶음에 다 모이지 않을 수 있다. clustering 로직 변경은 승인 항목이라 손대지 않았다 - `[점수진단]`의
  묶음 기사 수로 먼저 확인한다.
- contentDemand(블로그+웹 20건 만점)는 바꾸지 않았지만 입력(블로그 수)이 늘어 포화되는 묶음이 많아진다.
  경쟁도 반영(`BLOG_COMPETITION_APPLY_TO_SCORE=true`) 중인 상위 60건은 백분위 기반이라 영향이 작다.
- 블로그 창은 날짜 단위라 뉴스보다 넓다(18시 실행 기준 ~42시간).
