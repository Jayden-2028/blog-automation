# 이미지 기획 단계 설계 (A안) — 2026-10-01

## 왜 필요한가

**"이 자리가 실제로 무엇을 보여줘야 하는가"를 판단하는 주체가 지금 없다.**

집필자는 검색 결과를 **보기 전에** 자리 설명·검색어·획득 방식을 전부 정한다. 수집기는 그 지시를
그대로 받아 실행만 한다. 둘 사이에 "이 지시가 맞는가"를 묻는 단계가 없다.

실측 두 건(2026-10-01).

**① 기안장2 — 자리 6개 중 2개만 채워졌다. 원고의 주인공이 한 장도 없다.**

```
원고 메인: 덱스가 기안장2에 합류한다
마커:     기안84 옆에서 일손을 돕는 덱스 — 웹 검색
검색어:   덱스 기안84
결과:     없음
```

그 회차가 아직 방영되지 않아 **그런 사진은 존재할 수 없다.** 집필자는 그걸 모른 채 썼고,
수집기는 "없다"고 정직하게 포기했다. 아무도 "그럼 덱스 프로필이라도 넣자"로 돌리지 않았다.

**② 폭설 — 지시와 결과가 어긋났다.**

```
원고 한 줄: 영화 폭설 1차 예고편 공개
마커:      공식 포스터 / 검색어: 영화 폭설 공식 포스터
결과:      예고편 장면이 들어옴
```

결과가 더 나았지만 **그건 우연이다.** 누구도 "이 원고의 1번은 예고편 장면이어야 한다"고 판단하지
않았다. 게다가 `폭설`은 동명 작품이 있어 배우명 없이 검색하면 다른 작품이 섞인다 — 사용자가 직접
찾을 때는 `영화 폭설 김윤석 구교환 예고편`으로 중의성을 없앴다.

## 바꾸는 것 — 역할 재배치 (A안, 2026-10-01 사용자 결정)

| | 지금 | A안 |
|---|---|---|
| 자리 개수·위치 | 집필자 | 집필자 (그대로) |
| **무엇을 보여줄지** | 집필자 | 집필자가 **한 줄 힌트**, 기획이 확정 |
| **검색어** | 집필자 | **기획** |
| **획득 방식** | 집필자 | **기획** |
| 어디서 찾을지(서치풀) | 수집기(카테고리 고정) | **기획**(자리마다) |
| 후보 중 고르기 | 선택 에이전트 | 선택 에이전트 (그대로) |

집필자는 **본문을 쓰는 사람**으로 돌아간다. 검색 결과를 예측하는 일에서 손을 뗀다.

## 새 단계 — 이미지 기획 (`planImageSlots`)

원고 1건당 **LLM 한 번**. 자리 전부를 한 번에 기획한다.

### 입력

- 원고 전문(마커 포함)
- 자리별 **바로 위 문단**
- 집필자 마커 설명(힌트)
- **오늘 날짜** ← 시점 판단에 필수다
- 리서치 파일 전문(`## 11. 캡처할 페이지`의 URL 포함)
- 카테고리

### 출력 (JSON)

```json
{
  "summary": "영화 폭설 1차 예고편 공개",
  "slots": [
    {
      "index": 1,
      "subject": "영화 폭설 1차 예고편의 눈 덮인 선로 장면",
      "queries": ["영화 폭설 김윤석 구교환 예고편", "폭설 예고편 스틸"],
      "acquisition": "search",
      "changed": true,
      "reason": "원고 한 줄이 '예고편 공개'다. 포스터보다 예고편 장면이 맞다.",
      "caution": "동명 작품이 있어 배우명을 검색어에 넣었다"
    }
  ]
}
```

`reason`과 `caution`은 **사람이 읽는 값**이다. 뷰어의 수집 기록(2단계에서 만든 자리)에 그대로
실어 "왜 이 검색어가 됐는지"를 보게 한다.

### 기획이 따르는 규칙

**R1. 원고를 한 줄로 요약하고, 1번 자리는 그 한 줄을 보여준다.**
"예고편 공개"가 한 줄이면 1번은 예고편 장면이다. 포스터도 배우 사진도 아니다.

**R2. 중의성을 없앤다.** 작품·인물명이 흔하면 **배우명·연도·장르**를 검색어에 붙인다.

```
(X) 폭설 예고편            → 동명 작품이 섞인다
(O) 영화 폭설 김윤석 구교환 예고편
```

**R3. 시점을 검증한다.** 오늘 날짜 기준으로 **아직 일어나지 않은 장면은 존재하지 않는다.**
방영 전 회차, 개봉 전 장면, 예정된 행사 현장이 여기 해당한다. 그럴 때는 **대상을 바꾼다.**

```
(X) 기안84 옆에서 일손을 돕는 덱스   → 방영 전이라 없다
(O) 덱스 프로필 / 덱스 예능 출연 사진 → 출연 발표 맥락에서 쓸 수 있다
```

**R4. 주인공을 지킨다.** 원고의 주인공이 **전체 이미지에 한 번도 없으면 그 원고는 실패다.**
기획은 최소 한 자리를 주인공 단독 사진으로 잡는다.

**R5. 검색어는 이름 2~4단어.** 장면을 서술하지 않는다. **회차(1차/2차/3차)를 넣지 않는다** —
회차를 넣으면 번인 자막이 박힌 티저 썸네일이 올라온다.

**R6. 자리를 비우느니 대상을 바꾼다.** 단, 바꾼 대상이 문단과 무관하면 그때는 비운다.
(§"없으니까 대신 이거" 금지는 **같은 주제 안에서의 대체**에는 적용하지 않는다.)

### 두 사례에 적용하면

| | 지금 | 기획 후 |
|---|---|---|
| 폭설 1번 | `영화 폭설 공식 포스터` | `영화 폭설 김윤석 구교환 예고편` (R1·R2) |
| 기안장2 3번 | `덱스 기안84` → 빈 자리 | `덱스 프로필` (R3·R4) |
| 닥터X 1번 | `닥터X 하얀 마피아의 시대 스틸컷` | `닥터X 김지원` — 회차 빼고 인물 중심 (R5) |

## 파이프라인 배치

```
승인 → prepareManuscript
        ├ removeTableMarkers / alignImagePrompts   (지금 그대로)
        ├ ★ planImageSlots                         ← 새 단계
        ├ capturePagesForJob      (기획의 acquisition=capture 자리)
        ├ collectWebImagesForJob  (기획의 queries를 쓴다)
        └ buildFallbackImagePrompts → AI 생성
```

- 멱등 게이트: `metadata.imagePlanReadyAt`. 이미 기획했으면 건너뛴다.
- 결과는 `metadata.imagePlan`에 저장한다. 재수집할 때 다시 기획하지 않는다.
- **기획이 실패하면 집필자 마커로 돈다**(fail-open). 이미지가 통째로 사라지는 것보다 낫다.

## 집필자 규격에서 덜어내는 것

`prompts/writing/rules/images.md`(669줄)에서 **검색 결과를 예측하는 규칙**이 빠진다.

| 절 | 지금 | A안 |
|---|---|---|
| §8-1-1 검색어 쓰는 법(이름으로 찾기) | 집필자 | → 이미지 메이커 |
| §8-4 세 갈래 판정(획득 방식) | 집필자 | → 이미지 메이커 |
| §8-6 웹 검색으로 주문하면 안 되는 것 | 집필자 | → 이미지 메이커 |
| §8-7 카테고리별 서치풀 | 집필자 | → 이미지 메이커 |
| 자리 개수·위치, 문단과의 관계 | 집필자 | **그대로** |
| §8-5 상징물로 갈아타지 않기 | 집필자 | **그대로**(자리 설계 원칙) |

**마커 형식도 바뀐다.**

```
지금:  [IMAGE: 수술복 차림의 김지원 — 웹 검색]
       [IMAGE PROMPT: 닥터X 하얀 마피아의 시대 스틸컷]

A안:   [IMAGE: 수술복 차림의 김지원]
```

꼬리와 프롬프트 줄이 사라진다. 옛 원고의 꼬리는 **힌트로 계속 읽는다**(하위 호환).

⚠️ 영향 받는 코드: `parseManuscriptBlocks`(프롬프트 짝 맞추기), `articleReviewChecks`의
`checkImagePrompts`, `refixImageMarkers`. 프롬프트가 없는 것이 **정상**이 되므로 검사도 바꿔야 한다.

## 코드로 거는 안전장치

**주인공 커버리지 검사(R4).** 원고 키워드의 인물명이 **캡션 어디에도 없으면** 경고를 수집 기록에
남긴다. 기안장2는 이 검사에 바로 걸린다. LLM 판단이 아니라 문자열 대조라 싸고 확실하다.

## 비용·위험·되돌리기

- **비용**: 원고당 LLM 1회. 이미 조사·집필·수집·선택·검증으로 여러 번 부르고 있어 비중은 작다.
- **위험 1 — 기획이 집필자 의도를 뭉갠다.** → 마커를 힌트로 넘기고, 바꾼 이유(`reason`)를
  뷰어에 남긴다. 사람이 보고 `🖼 이미지 수정`으로 되돌릴 수 있다.
- **위험 2 — 기획이 틀린 검색어를 만든다.** → 지금도 집필자가 틀린 검색어를 만든다. 다른 점은
  기획은 **문단과 날짜를 보고** 만든다는 것이다. 드라이런으로 먼저 비교한다(아래).
- **되돌리기**: `IMAGE_PLANNING=false`면 집필자 마커로 돈다. 코드 경로가 그대로 남는다.

## 작업 순서와 검증

**1단계 — 드라이런 (코드 변경 없음, 비용 작음)**
어제·오늘 원고 10건에 기획만 돌려 **집필자 검색어 vs 기획 검색어**를 표로 뽑는다. 사람이 보고
"이게 더 낫다"가 확인되면 진행한다. 수집은 돌리지 않으므로 이미지 비용이 0이다.

**2단계 — 기획 단계 구현**
`planImageSlots.ts` + 프롬프트(`image-maker.md`에 기획 절 추가) + 테스트.
`IMAGE_PLANNING=false` 기본으로 넣어 운영에 영향 없이 병합한다.

**3단계 — 수집 배선**
`collectWebImagesForJob`이 기획의 `queries`·`acquisition`을 쓴다. 기록을 뷰어에 남긴다.

**4단계 — 켜기**
`IMAGE_PLANNING=true`. 원고 몇 건을 눈으로 보고 충족률·주인공 커버리지를 비교한다.

**5단계 — 집필자 규격 정리**
위 표대로 `images.md`를 덜어낸다. **4단계가 좋을 때만** 한다 — 먼저 지우면 되돌릴 곳이 없다.

## 사용자 결정이 필요한 것

1. **마커에서 꼬리·프롬프트를 지우는 시점.** 2~4단계에서는 집필자가 지금처럼 써도 되고(기획이
   무시한다), 5단계에서 지운다. 더 일찍 지우면 기획이 힌트를 잃는다.
2. **기획을 사람이 미리 보고 고칠 수 있게 할지.** 승인 직후 기획 결과를 텔레그램으로 먼저 보여주고
   OK를 받는 흐름을 넣을 수 있다. 품질은 오르지만 버튼이 하나 늘어난다.
3. **드라이런 표본 수.** 10건이면 하루치다. 더 보고 싶으면 늘린다.
