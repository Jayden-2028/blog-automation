# 티스토리 자동 발행 설계 (2026-10-06, 사회 이슈 트랙)

> 전제(사용자 확정): 사회 트랙은 사용자가 대부분 PC 뷰어로 본다 → **로그인이 풀리면 사용자가 언제든 개입해 다시 로그인할 수 있다.**
> 이 전제가 2026-09-15에 티스토리를 접은 이유(로그인 풀림을 무인으로 못 넘김)를 뒤집는다. 그래서 설계의 핵심은 "로그인 안 풀리게"가 아니라 **"풀렸을 때 사람이 1분 안에 복구하고, 대기 중이던 발행이 알아서 이어지게"** 다.

## 결정 (2026-10-06 사용자 확정)

- 브라우저 실행 위치: **맥미니** (네이버 폴러와 같은 구조). 재로그인은 맥미니 화면 공유로.
- 이미지: **처음부터 티스토리에 업로드**(핫링크 단계 없음). §4의 A안으로 바로 간다.
- 로그인 풀림으로 미뤄진 발행: **3일 지나면 자동 재개하지 않고** 사람이 버튼을 다시 눌러야 한다.

## 0. 한 줄 요약

네이버 발행 경로를 그대로 복제한다. **버튼(텔레그램·뷰어 어느 쪽이든) → `job.metadata.tistoryPublish` 큐 → 맥미니 폴러가 로그인된 브라우저로 발행.** 다른 점은 둘: ① 로그인 풀림을 "실패"가 아니라 **"대기(deferred)"** 로 두고 재로그인 후 자동 재개, ② 발행 전 로그인 상태를 **미리** 점검해 알린다.

## 1. 흐름

```
[텔레그램 🟠 티스토리 발행]  ─┐
                              ├─→ requestTistoryPublish(job)  (job.metadata.tistoryPublish = requested)
[뷰어 🟠 티스토리 발행 버튼] ─┘        │
   (Pages Function → repository_dispatch → GH Actions)
                                       ↓  맥미니 launchd  tistory-poll (60초)
                              publishJobToTistory(jobId)
                                 ├─ 로그인 OK  → 제목/본문/태그/카테고리/공개범위 → 발행 → publications(platform=tistory) → 사회 봇 알림 "올라갔습니다 + URL"
                                 └─ 로그인 풀림 → status=deferred(reason=login) → 사회 봇 알림 1회 "로그인 필요" → 다음 폴링에서 재시도
```

- 큐·중복 방지·결과 기록은 `naverPublishQueue.ts`·`publishJobToNaver.ts`와 같은 모양(jsonb 키 `tistoryPublish`, `publications` 테이블에 `platform="tistory"`). **migration 없음.**
- 발행 원고는 네이버와 같이 `pickFinalArticle` → `articles.content`를 읽는다. 사회 트랙 전용 가공: `참고 자료` 링크아웃은 **유지**(티스토리는 바깥 링크 OK), 블로그스팟 내부 링크 "함께 보면 좋은 글"은 **제거**(다른 블로그로 가는 링크).
- 공개 범위: 기본 **비공개**, `TISTORY_PUBLISH_VISIBILITY=public`으로 공개(네이버와 같은 첫 운영 원칙). 카테고리는 `config/tistoryCategoryMapping.ts`(job.category → 티스토리 카테고리 id).

## 2. 뷰어에서 고친 내용으로 발행되게

이미 해결돼 있다. 뷰어의 "📤 수정본 반영"이 `articles.content`를 **먼저** 쓰고(`applyViewerEditRequest.ts`), 발행은 그 내용을 읽는다. 티스토리도 같은 함수를 타므로 추가 작업이 없다. 단 **한 가지 구멍**을 막아야 한다:

- 뷰어에서 고치기만 하고(브라우저 localStorage) "반영"을 안 누른 채 발행 버튼을 누르면 **옛 글이 올라간다.**
- 대책: 뷰어의 티스토리 발행 버튼은 **반영 안 된 수정이 있으면 누를 수 없게** 한다("먼저 📤 수정본 반영을 눌러주세요"). 반영은 비동기(1~2분)라, 반영 완료가 페이지에 표시된 뒤에만 발행 버튼이 열린다.
- 텔레그램 버튼은 localStorage를 모른다. DB에 있는 글(=마지막 반영본)이 올라간다. 알림 문구에 그 사실을 적는다.

## 3. 로그인 풀림 대응 (이 설계의 핵심)

| 상황 | 동작 |
|---|---|
| 발행 중 로그인 화면으로 튕김 | `deferred(login)`로 기록, **실패로 치지 않는다.** 사회 봇으로 "🔑 티스토리 로그인이 풀렸습니다. 맥미니에서 `npm run setup:tistory`로 로그인하면 대기 중 N건이 자동으로 올라갑니다" 1회 알림(같은 사유로 반복 알림 안 함) |
| 재로그인 후 | 다음 폴링(60초)에서 deferred 건을 다시 집어 발행. 사람이 버튼을 다시 누를 필요 없음 |
| 발행 요청이 없을 때 | 폴러가 **하루 1회(19:30, 20시 리포트 직전)** 로그인 상태만 가볍게 확인. 풀려 있으면 미리 알림 → 사용자가 리포트 보기 전에 로그인해 둔다 |
| 로그인 세션 연장 | 로그인 시 카카오 "로그인 상태 유지" 체크 안내 + 폴러가 점검 때 관리 페이지를 한 번 열어 쿠키 갱신(효과는 실측으로 확인, 보장 없음) |
| 네이버 폴러와 충돌 | 티스토리는 TinyMCE API(`setContent`)로 본문을 넣어 **클립보드·창 포커스를 쓰지 않는다** → headless로 돌려 네이버(headed+클립보드)와 동시에 돌아도 방해하지 않는다. 로그인만 `setup:tistory`를 headed로 사람이 한다 |

"자동 재시도는 없다"는 운영 규칙(CLAUDE.md)은 **진짜 실패**(본문 반영 실패, 발행 버튼 오류)에만 적용한다. 로그인 풀림은 실패가 아니라 대기다.

## 4. 이미지 (결정 필요)

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. 티스토리에 업로드** (권장) | 대표이미지 잡힘, 글이 Supabase에 의존하지 않음(10-04에 Supabase 이미지 189개를 정리한 전례 — 핫링크면 그때 글이 깨진다) | 에디터 "사진" 버튼 → 파일 선택창 → 본문 커서 위치 삽입을 Playwright로 해야 함. 네이버 쪽에서 방금 겪은 파일 선택창·캡션 재시도 문제가 똑같이 나올 수 있음. **구현·실측 기간의 대부분이 여기** |
| B. `<img src=Supabase URL>` 핫링크 | TinyMCE `setContent` 한 번으로 끝. 하루면 됨 | 대표이미지 안 잡힘(썸네일 없음), Supabase 트래픽, 이미지 정리하면 글 깨짐 |

권장: **A를 목표로 하되, 1차는 B로 돌려 흐름(버튼→큐→발행→알림)을 먼저 검증**하고, 2차에 A로 교체. B로 올린 글은 2차 전까지 Supabase 이미지를 지우지 않는다.

## 5. 뷰어 발행 버튼

- `social.html`에만 "🟠 티스토리 발행" 버튼(엔터 뷰어는 변경 없음 — 네이버 버튼은 별도 과제).
- 경로: 뷰어 → Pages Function `POST /api/publish-request`(기존 `manuscript-edit`와 같은 Access JWT 검증·같은 Function 구조) → `repository_dispatch(publish_request, {jobId, channel:"tistory"})` → GH Actions `publish-request.yml` → `requestTistoryPublish(jobId)`.
- 텔레그램 버튼과 **같은 큐**에 들어가므로 둘 다 눌러도 1건만 올라간다(네이버와 같은 중복 가드).
- 버튼 상태: 대기 중/발행됨/로그인 대기를 뷰어에 표시(`manuscript_manifest_topics`의 `tistoryPublish` 상태를 페이지 재배포 때 같이 그림).

## 7. 예상되는 다른 문제

1. **DOM 변경**: 2026-08-31 셀렉터(`#post-title-inp`, `editor-tistory`, `#tagText`)가 지금도 맞는지 모른다. 0단계 스냅샷 전에는 발행기를 못 짠다.
2. **헤드리스 로그인 세션 공유**: 사람이 headed로 로그인한 프로필을 headless가 그대로 쓸 수 있어야 한다. 옛 코드는 임시저장까지 이 방식으로 됐지만, 카카오가 headless를 다르게 볼 가능성은 남아 있다. 안 되면 티스토리도 headed로 돌리고 네이버 폴러와 **같은 락**으로 직렬화한다(네이버 폴러는 다른 세션 소유라 조율 필요).
3. **맥미니 화면 접근**: 재로그인은 맥미니에서 해야 한다. 사용자가 PC에서 맥미니 화면 공유로 들어가는 동선이 확보돼 있어야 "언제든 개입" 전제가 성립한다. 아니면 이 폴러만 사용자 PC(이 맥)에서 돌리는 선택지가 있는데, 그 PC가 꺼져 있으면 발행이 밀린다.
4. **약관·제재**: 티스토리는 공식 발행 API가 없고 브라우저 자동화는 약관상 회색지대다. 하루 몇 건 수준이면 실측상 문제가 없었지만, 저품질·제한 판정 위험은 0이 아니다. 발행 간격은 코드로 강제하지 않고 사람이 판단한다(네이버와 같은 결정).
5. **첫 발행은 비공개**: 서식·이미지·카테고리를 눈으로 확인한 뒤 `public`으로 바꾼다. 비공개 글을 공개로 바꾸는 건 사람이 티스토리에서 한다(초안을 다시 여는 자동화는 네이버 때 팝업 문제로 포기한 전례).
6. **알림 채널**: 발행 결과·로그인 알림은 사회 봇(`notifierForJob`)으로 간다. 네이버 폴러는 메인봇을 쓰는데 이건 다른 세션 소유라 손대지 않는다.
7. **큐 적체**: 로그인이 며칠 풀린 채 요청이 쌓이면 재로그인 직후 한꺼번에 올라간다. 폴러는 1회 2건 상한이라 2분 간격으로 순차 발행되지만, 묵은 글이 뒤늦게 공개되는 게 싫으면 "N일 지난 deferred는 사람이 다시 눌러야 함"을 둔다(기본 3일 제안).
