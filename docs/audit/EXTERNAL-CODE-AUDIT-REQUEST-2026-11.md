## 1. 의뢰 배경 — 솔직한 자기 진단

이 시스템은 2026-08-24에 시작해 **83일 동안 806개 커밋**이 쌓였습니다(하루 평균 9.7커밋).
개발 방식은 LLM 에이전트(Claude Code)가 설계·구현하고 사람이 승인하는 형태였고, 그 결과
**"고치면서 자란" 흔적이 코드 전반에 남아 있습니다.**

의뢰인이 체감하는 문제는 두 가지입니다.

1. **파이프라인 자체는 만족스럽다.** 수집 → 조사 → 집필 → 이미지 → 검수 → 발행 흐름은 의도대로
   동작하고, 결과물도 받아들일 수 있는 수준입니다. 그래서 **흐름을 바꾸는 제안은 원하지 않습니다.**
2. **그런데 코드가 필요 이상으로 무겁다는 느낌이 있다.** 반복된 수정·확장 과정에서 쓰이지 않게 된
   분기, 측정만 하고 치우지 않은 실험 플래그, 한 번 돌고 남은 백필 작업, 비대해진 규격 문서가
   남아 있을 것으로 의심합니다. 이런 찌꺼기가 (a) 간헐적 오류의 원인이 되거나 (b) LLM 호출 때마다
   토큰을 먹고 있다면, 그건 **보이지 않는 고정 비용**입니다.

이 감사는 그 **의심을 실측으로 확정하거나 기각하고, 안전하게 걷어낼 목록을 받는 것**이 목적입니다.

### 1-1. 의뢰인이 감사인에게 미리 밝히는 전제

- 우리는 자체 실측을 일부 해 봤고, **그 결과를 §3과 §7에 숨기지 않고 적었습니다.** 유리한 쪽만
  보고하지 않았습니다. 예컨대 "고아 파일이 수두룩할 것"이라는 우리 가설은 실측에서 **거의 기각**
  됐습니다(§7-1).
- 우리 실측은 정적 grep 수준입니다. **전문 도구(`knip`, `ts-prune`, 커버리지, 런타임 트레이싱)로
  다시 재 주시기를 요청합니다.** 우리 숫자를 믿지 말고 베이스라인으로만 쓰십시오.
- 가장 아프지만 중요한 지점: **우리는 줄이고 싶어하는 비용을 현재 측정하지 못합니다.** §4-3을
  읽어 주십시오.

## 2. 시스템 개요 (감사인이 알아야 하는 최소한)

### 2-1. 무엇을 하는 시스템인가

한국어 블로그 3채널을 자동 운영합니다.

| 채널 | 플랫폼 | 언어 | 성격 |
| --- | --- | --- | --- |
| 엔터/트렌드/사회 | Tistory + Blogspot | 한국어 | 시사·연예·사회 이슈 |
| Korea Plain | Blogspot (`www.koreaplain.com`) | **영어** | 해외 독자용 한국 생활 안내 |
| 육아 | Naver Blog | 한국어 | 개인 블로그 톤 |

### 2-2. 실행 구조

- **오케스트레이션**: Node.js + TypeScript. **Node는 조율만 하고 판단하지 않는다**는 원칙이 있습니다
  (규격은 전부 마크다운 프롬프트 파일에 있고, LLM이 그걸 읽고 따릅니다).
- **실행 환경 3곳**:
  1. GitHub Actions (워크플로 25개) — 수집·조사·집필·발행 본체
  2. Cloudflare Workers / Pages — 텔레그램 릴레이, 원고 뷰어
  3. 맥미니 (launchd) — 상시 구동 작업(티스토리 세션 유지 등)
- **상태 저장**: Supabase(PostgreSQL), migration 20개
- **LLM**: Claude Code headless CLI (`claude -p`)가 주력. 보조로 Gemini(자료조사 대안),
  OpenAI `gpt-image-2`(이미지 생성), Serper(검색)
- **사람의 개입 지점**: 텔레그램 봇. 키워드 승인(Go), 원고 검수, 발행 승인

### 2-3. 설계 규칙 (감사 제안이 충돌하면 안 되는 것)

저장소 루트 `CLAUDE.md`에 운영 규칙이 있습니다. 감사와 직접 관련된 것:

- **"왜"를 주석으로 남긴다.** 사고가 났던 자리에는 날짜와 원인을 적습니다. → **§5-4 참조. 이
  주석은 군살이 아닙니다.**
- **규격은 코드가 아니라 `prompts/**/*.md`에 있다.** 문체·사실 태도·서식 규칙을 코드로 옮기는
  제안은 이 원칙에 반합니다.
- 승인 없이 금지: 운영 DB 쓰기, migration 적용, 외부 메시지 발송, 발행 게이트 변수 변경,
  파괴적 Git 작업.

## 4. 감사 목표 — 세 가지

### 4-1. 목표 A — 사문화된 코드 식별

실제로 실행되지 않는 코드를 **증거와 함께** 목록화해 주십시오.

의심 근거(우리 실측):

- **환경변수 130개를 코드가 읽는데, 운영에 실제로 설정된 것은 44개뿐입니다.**
  (GitHub repo variables 15개 + secrets 29개. 맥미니 로컬 `.env`는 비밀값이라 감사 범위 밖이며,
  필요하면 변수 **이름 목록만** 제공합니다.)
- 코드가 읽지만 `.env.example`에도 없는 변수 **37개**. 그중 실험·관측용으로 보이는 것:
  `ENT_TREND_GATE_PREVIEW`, `ENT_TREND_GATE_APPLY`, `ENT_TOPIC_CONFLICT_PREVIEW`,
  `ENT_TOPIC_CONFLICT_DROP`, `TOPIC_MERGE_PREVIEW_ENABLED`, `DIVERSITY_TOPIC_QUERY_PREVIEW`,
  `BLOG_COMPETITION_PROBE_ENABLED`, `BLOG_COMPETITION_SKIP_FALLBACK`, `ENT_NEWS_FEED_ENABLED`,
  `GOOGLE_TRENDS_ENABLED`, `PERSON_AI_TAB`, `PERSON_AI_TAB_HEADFUL`
  → **이것들이 "관측하고 치우지 않은 실험"이라면 정확히 이 감사가 찾는 찌꺼기입니다.**
  각 플래그가 (a) 켜진 적 있는가 (b) 지금 꺼져 있으면 그 분기가 죽은 코드인가를 판정해 주십시오.
- 폐기 표시가 코드에 남아 있습니다: `폐지` 83회/47파일, `쓰지 않는다` 340회/134파일,
  `더 이상` 25회/22파일, `하위 호환` 13회/7파일.
  → 이 중 **"폐지라고 적어 두고 코드는 남겨 둔 것"**을 구분해 주십시오.
- **90일 가까이 실행되지 않은 워크플로**:

  | 워크플로 | 마지막 실행 | 우리 추정 |
  | --- | --- | --- |
  | `tkm-rebrand.yml` | 2026-10-27 | 일회성 리브랜딩 백필, 완료 |
  | `tkm-structure-backfill.yml` | 2026-10-29 | 일회성 구조 백필, 완료 |
  | `manuscript-edit.yml` | 2026-10-29 | 사용 안 하게 된 것으로 추정 |
  | `analytics-ga4.yml` | 2026-10-08 | 미확인 — **살아 있어야 하는데 죽은 것일 수 있음** |

  마지막 항목처럼 **"죽은 게 아니라 고장난 것"을 반드시 구분**해 주십시오. 지우면 안 되는 걸
  지우는 것이 이 감사 최대의 리스크입니다.

### 4-2. 목표 B — 찌꺼기가 유발하는 오류 경로 식별

과거에 실제로 난 사고 유형 중, **원인이 "남아 있던 옛 코드"였던 패턴**을 찾아 주십시오.
우리가 겪은 실례(참고용, 모두 이미 수정됨):

- 규격 문서를 분리했는데 **한쪽만 갱신돼 두 경로가 다른 규칙을 적용**했다
  (`buildWritingPrompt` vs `reviseArticleWithFeedback` → `specFiles.ts`로 단일화해 해결).
- 디스패치 재시도 로직이 **Worker와 Node에 두 벌 존재**해 한쪽만 고쳐져 500 에러로 작업이 죽었다.
- `continue-on-error: true` 스텝이 **실패를 success로 덮어** 진짜 원인을 가렸다.

→ 같은 모양의 문제가 **지금도 남아 있는지** 봐 주십시오. 특히:

1. **동일 로직의 중복 구현.** 같은 이름의 export가 여러 곳에 있습니다:
   `normalizeTitle`(3곳), `readImageSize`·`normalizeUrl`·`isTistoryLoginUrl`·`extractImageMarkers`·
   `describeError`·`decodeEntities`(각 2곳). 이름이 같은데 **동작이 미묘하게 다르면** 그게
   다음 사고입니다.
2. **테스트에서만 참조되는 운영 코드** 9파일 / 1,183줄 (§7-1에 목록). 단, Cloudflare 엔트리포인트는
   오탐입니다 — `wrangler`가 배포하므로 import되지 않는 게 정상입니다.
3. **`continue-on-error`로 실패를 가리는 스텝**이 워크플로 25개에 몇 개나 있고, 각각이
   실패를 삼키고 있는지.
4. 같은 상태를 **두 곳에 저장**하는 구간(DB `metadata` JSON vs 전용 테이블). 과거 lost update
   사고의 원인이었습니다.

### 4-3. 목표 C — LLM 토큰 다이어트 ★ 최우선

**이것이 이번 감사의 핵심이며, 동시에 우리가 가장 솔직해야 하는 부분입니다.**

#### (1) 우리는 줄이고 싶은 비용을 측정하지 못합니다

`src/config/apiPricing.ts`가 단가를 관리하는 유일한 지점인데, **등록된 모델은
OpenAI `gpt-image-2`, Gemini 2종, Serper뿐입니다. Claude가 없습니다.**
이유는 Claude를 구독(`CLAUDE_CODE_OAUTH_TOKEN`)으로 쓰기 때문입니다 — 호출당 청구서가
오지 않고, 대신 **플랜 한도를 먹습니다.**

결과적으로 **가장 많이 쓰는 LLM의 사용량이 우리 비용 대시보드에 한 줄도 안 잡힙니다.**
이건 감사 대상이자 감사의 제약입니다. 감사인은 토큰 소비를 **프롬프트 입력 크기로 역산**해야
합니다. 아래 수치가 그 출발점입니다.

#### (2) 집필 1회당 입력 페이로드 실측

점검 요청:

- `images.md` 30,050자 — 이미지 마커를 **본문에 삽입하는 규칙**에 3만 자가 필요한가?
  마커 생성 단계와 실제 이미지 획득 단계(별도 LLM 호출)가 같은 문서를 공유하면서
  **집필 단계에 불필요한 획득 로직까지 실려 있지 않은지** 봐 주십시오.
- `docs/seo-guide.md` 20,288자 — 목록에 "충돌 시 위 문서가 이긴다"고 **가장 낮은 우선순위로**
  적혀 있습니다. 매번 2만 자를 읽히면서 우선순위는 최하위라면, 수치 규칙만 추출할 수 있는지.
- **중복 규칙.** 9개 문서가 서로를 참조하며 "이건 여기 있다"고 안내합니다. 같은 규칙이 2~3곳에
  다른 말로 적혀 있지 않은지 대조해 주십시오.
- `writer.md` 안에 **이미 사문화된 지시**가 있습니다: §2의 스킬 라우팅(`/parenting-blog-writer` 등)은

## 5. 절대 제약 — 건드리면 안 되는 것

**이 절을 위반하는 제안은 채택되지 않습니다.** 감사인은 제안마다 이 절과의 충돌 여부를
스스로 명시해 주십시오.

### 5-1. 파이프라인 동작은 1바이트도 바꾸지 않는다

- 수집 → 조사 → 집필 → 이미지 → 검수 → 발행 **순서와 단계 구성 불변**
- 사람의 승인 지점(텔레그램 Go / 검수 / 발행 승인) **불변**
- **원고 결과물이 달라지는 변경 금지.** 프롬프트를 줄여서 문체·구조·분량·사실 태도가 바뀐다면
  그건 다이어트가 아니라 사양 변경입니다.
- `final 6-factor scoring`, relevance, clustering 로직 **변경 금지**(별도 승인 사항)

### 5-2. 운영 중인 것을 멈추지 않는다

- GitHub Actions 워크플로의 **트리거·스케줄·concurrency 그룹** 변경 금지
- 맥미니 launchd 잡과 포트 **변경 금지**
- Supabase migration 적용·history 변경 **금지** (제안만)
- 발행 게이트 변수(`BLOGGER_ENABLED`, `TISTORY_PUBLISH_MODE` 등) **변경 금지**
- 운영 DB 쓰기(insert/update/delete/backfill) **금지**. 읽기만 하십시오.
- 외부 메시지 발송(텔레그램 등) **금지**. 테스트는 더미 자격증명으로:
  `SUPABASE_URL=https://dummy.invalid SUPABASE_SERVICE_ROLE_KEY=dummy-not-a-real-key`
  (과거에 운영 `.env`로 테스트를 돌려 실제 텔레그램 메시지가 발송된 사고가 있었습니다.)

### 5-3. 비밀값에 접근하지 않는다

`.env`, 인증 토큰, 브라우저 로그인 프로필을 열거나 출력하지 마십시오. 변수 **이름**이 필요하면
요청해 주십시오.

### 5-4. "왜" 주석은 군살이 아니다 ★

비테스트 코드의 **24.3%가 주석**이고, **날짜 스탬프가 521개 파일에 2,607개** 있습니다.
수치만 보면 명백한 다이어트 대상처럼 보입니다. **아닙니다.**

이 주석들은 사고가 났던 자리에 "무슨 일이 있었고 왜 이렇게 됐는지"를 남긴 것이며,
LLM 에이전트가 개발하는 이 프로젝트에서 **동일 사고의 재발을 막는 유일한 장치**입니다.
주석은 **LLM 호출 비용에 포함되지 않습니다**(코드 파일은 프롬프트로 전송되지 않습니다).
즉 토큰 비용 0, 재발 방지 효과 큼 — **지우면 손해만 남습니다.**

→ **주석 삭제·압축 제안은 받지 않습니다.** 단, 다음은 예외적으로 보고해 주십시오:
  - 주석이 설명하는 **코드가 이미 사라졌는데 주석만 남은 경우**
  - 주석이 **사실과 다른 경우**(코드가 바뀌었는데 주석이 안 바뀜) — 이건 삭제가 아니라
    **수정 대상**이며, 오히려 적극적으로 찾아 주십시오.

### 5-5. 테스트를 줄이지 않는다

테스트가 전체 코드의 33.5%(207파일 / 37,157줄), `test:*` npm script가 219개입니다.
무거워 보이지만 **이 프로젝트는 운영 DB와 외부 API에 붙어 있어 테스트가 유일한 안전망**입니다.

→ 테스트 **삭제 제안은 받지 않습니다.** 다음만 보고해 주십시오:
  - **같은 것을 두 번 검증하는 중복 테스트**
  - **단정문이 없는 테스트**(돌기만 하고 아무것도 검증하지 않는 것)
  - 219개 script의 **네이밍·그룹화 정리안**(실행 방식 개선, 삭제 아님)

### 5-6. 기술 스택을 바꾸지 않는다

프레임워크 도입, 빌드 도구 교체, 모노레포 전환, ORM 도입, 린터 규칙 전면 변경 — 전부 범위 밖입니다.
`tsc`가 3.9초에 깨끗하게 통과하는 현 상태가 기준선입니다.
